## 一条命令（在服务器上）

```bash

```

它按顺序检查：

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | `systemctl is-active siyige` | `active` |
| 2 | 应用自身 `127.0.0.1:8090/api/health` | `ok:true` |
| 3 | **公网入口** `127.0.0.1:8787/siyige/api/health` | `ok:true` |
| 4 | 静态页 `8787/siyige/v2/index.html` | 200 且 >500 字节 |
| 5 | 题库接口 `8787/siyige/api/topics` | 200 且 >500 字节 |
| 6 | lifekit 代理里是否还有 siyige 路由 | `grep proxyToSiyige` 命中 |

任何一条不过就打印原因并以非 0 退出。

## Windows 侧两条运维脚本（scripts/ops/）

```powershell
# 自检：应用自身 + 反代后 + 站点根 + 前端产物 + Redis
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\healthcheck.ps1 `
  -DirectBase http://127.0.0.1:8080 `
  -PublicBase http://127.0.0.1:8787/siyige `
  -RedisHost 127.0.0.1 -RedisPort 6379 -RedisPassword siyige123456

# 备份：H2 数据文件 + server/config → backups\yyyyMMdd-HHmmss.zip，只留最近 7 份
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\backup.ps1
```

| 脚本 | 检查/产出 | 失败时看什么 |
|---|---|---|
| `healthcheck.ps1` | ① `DirectBase/api/health` 200 且 `"ok":true` ② `PublicBase/api/health` ③ `PublicBase/` ④ `PublicBase/v2/index.html`（>500B）⑤ Redis `PING`→`PONG`（redis-cli → `docker exec siyige-redis` → 裸 TCP `AUTH+PING` 依次尝试） | 脚本会逐项打 `[FAIL]` + 「排查：…」；任一项失败 **退出码 1** |
| `backup.ps1` | `backups\yyyyMMdd-HHmmss.zip`，内含 `server\config\**`、`data\**`（H2 `*.mv.db/*.trace.db/*.lock.db`）、`MANIFEST.txt`（含 git 版本） | 找不到可备份内容 → 退出码 1；H2 是内存库时会明确 WARN「只备份了配置」 |

几个参数的口径：

- `-DirectOnly`：只查应用自身 + Redis（本机调试，不经过反代）
- `-SkipRedis`：临时跳过 Redis（比如本地演示）
- `-Keep n` / `-KeepForever`：备份保留份数 / 不清理
- `-DataDirs <宿主数据目录>`：容器把 H2 落在仓库外时显式指定
- 执行策略报「禁止运行脚本」时加 `-ExecutionPolicy Bypass`（上面命令已带）

> `backups\*.zip` 里有 `server\config\application.yml`（含 LLM API Key 与支付签名密钥），
> **不要提交、不要外发**。`backups/` 目前不在 .gitignore 里，补规则要单独评审。

## 容器化上线（Dockerfile + docker-compose.yml）

### 0. 先决条件

| 项 | 要求 |
|---|---|
| 宿主 `server/config/application.yml` | 必须存在（**不进镜像**，运行时只读挂载到 `/app/config`）；线上要 `siyige.redis.enabled: true`、`pace.time-scale: 1.0`、换掉 `pay-secret` |
| Redis 密码 | `SIYIGE_REDIS_PASSWORD`（默认 `siyige123456`），compose 与容器内 `requirepass` 用同一个值 |
| 端口 | 宿主 8080 → 容器 8080，反代再挂 `/siyige` 前缀 |

`SIYIGE_*` 环境变量的优先级高于 `config/application.yml`，所以配置文件里残留的 dev 值（`redis.enabled: false`、`time-scale: 0.3`）会被 compose 里的 env 覆盖；改完记得两项都对一遍。

### 1. 构建 + 打 tag

```powershell
cd D:\siyige

# 记下当前在跑的版本，回滚要用
docker compose ps --format "{{.Image}}"
docker images --filter "reference=siyige-server" --format "{{.Repository}}:{{.Tag}}  {{.CreatedAt}}"

$PREV = (docker inspect siyige-server --format '{{.Config.Image}}') -replace '.*:',''   # 例如 20261125-090000
$TAG  = Get-Date -Format 'yyyyMMdd-HHmmss'

docker compose build                    # node 阶段构建前端 → maven 打包 → JRE 运行镜像
docker tag siyige-server:local "siyige-server:$TAG"
docker tag "siyige-server:$TAG" siyige-server:current
```

镜像里不含 `server/config/application.yml`（.dockerignore 排掉、只挂载），也不含 `data/`、`backups/`、`logs/`。

### 2. 起/更新

```powershell
# 升级前先备份（H2 文件库时尤其必须）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\backup.ps1

$env:TAG = $TAG
docker compose up -d                    # server 会等 redis 变 healthy 才启动
docker compose ps                       # 两个服务都要 healthy
docker compose logs -f --tail 100 server
```

### 3. 验证

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\healthcheck.ps1
node scripts/smoke_routes.mjs 9874 http://127.0.0.1:8787/siyige   # 需要 Chrome/Edge + CDP
```

三条都过才算上线成功：容器 `healthy`、`healthcheck.ps1` 退出码 0、页面冒烟全绿。

### 4. 回滚

```powershell
$env:TAG = $PREV                        # 回到上一版 tag，不要删旧镜像
docker compose up -d --no-build         # 用已有镜像重建容器，不重新构建
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\healthcheck.ps1
```

回滚注意：

- 只回滚镜像，**不回滚数据**。H2 文件库模式下新版本可能已经改过表结构，先 `backup.ps1` 留一份再升级。
- `redis-data` 是命名卷（`--appendonly yes`），回滚不清卷；要清得显式 `docker compose down -v`（会丢计数/未读/排行）。
- 旧 tag 至少保留两版（`current` + 前一版），`docker image prune` 不要带上 `siyige-server:*`。

## 日志在哪、怎么看

| 日志 | 位置 | 查看命令 |
|---|---|---|
| 容器 stdout/stderr（Spring 默认日志） | Docker `json-file` 驱动，单文件 20MB × 5 | `docker compose logs -f --tail 200 server` / `docker logs --since 30m siyige-server` |
| Redis | 同上 | `docker compose logs -f --tail 100 redis` |
| 应用挂载的日志目录 | 宿主 `.\logs` → 容器 `/app/logs` | `Get-Content .\logs\* -Tail 200 -Wait`（目前 resources/application.yml 没配 file appender，文件为空属正常，看 stdout） |
| 反向代理（lifekit 方案） | `/opt/lifekit/*.log` | `tail -f /opt/lifekit/server.log`、`journalctl -u lifekit -n 100` |
| 反向代理（nginx 方案） | `/var/log/nginx/` | `tail -f /var/log/nginx/error.log`、`grep siyige /var/log/nginx/access.log` |
| 进程模式（没上容器时） | systemd journal | `journalctl -u siyige -n 100 --no-pager`、`journalctl -u siyige --since "-10 min"` |
| 容器内路径速查 | `/app/app.jar`、`/app/config`（只读）、`/app/data`（H2）、`/app/logs` | `docker compose exec server ls -l /app` |

`HEALTHCHECK` 连续 3 次失败后容器变 `unhealthy`，`docker inspect siyige-server --format '{{json .State.Health}}'` 能看到最近几次探测的输出。

## `/siyige/` 整站 404 的排查顺序

按 ① 反代 location → ② 静态产物路径 → ③ base 的顺序查，前面的没问题再往后走，别跳步。

**① 反代 location（最常见，2026-11-24 就是这么挂的）**

```bash
# 应用自己通不通（容器内 8080）——通就说明问题在反代
curl -is http://127.0.0.1:8080/api/health | head -5
# 反代之后通不通
curl -is http://127.0.0.1:8787/siyige/api/health | head -5
```

- 8080 通、8787 挂 → 反代丢前缀：
  - lifekit 方案：`grep proxyToSiyige /opt/lifekit/server.cjs`，没有就 `python3 /tmp/fix_route.py && systemctl restart lifekit`
  - nginx 方案：`location /siyige/ { proxy_pass http://127.0.0.1:8080/; }` —— 末尾那个 `/` 决定**是否剥掉** `/siyige/` 前缀；两处（`proxy_pass` 和 `location`）多一个少一个斜杠，表现出来的就是整站 404
  - 只配了 `/siyige/api/` 没配 `/siyige/` 本身 → 首页 404 但接口正常
- 看 404 是谁回的：`curl -is …/siyige/v2/index.html`，`Server` 头是 nginx/Node 就是反代回的，是应用回的则看 ②
- WebSocket 另配：`/siyige/ws` 要带 `Upgrade`/`Connection` 头，不然房间功能静默失败

**② 静态产物路径（进了 jar 没有）**

```bash
# 直连应用，绕过反代
curl -is http://127.0.0.1:8080/v2/index.html | head -5
# 看产物是否真在包里
docker compose exec server sh -c 'unzip -l /app/app.jar | grep static/v2 | head'   # 容器内没 unzip 就拷出来看
jar tf server/target/siyige-backend-0.1.0.jar | grep 'static/v2/index.html'
```

- 直连 `/v2/index.html` 200 → 产物在，回去查 ①
- 直连也 404 → 前端产物没进 jar：确认 `web/vite.config.js` 的 `outDir` 仍是 `../server/src/main/resources/static/v2`，本地 `npm run build` 后把 `static/v2` 一起提交；CI 的「产物与仓库一致性」步骤就是拦这个
- 产物在但 `/siyige/v2/assets/*.js` 404 → 反代只转发了 HTML 没转发静态目录，或 `location` 规则优先级把 `assets` 吃掉

**③ base（页面能开但白屏/资源全 404）**

- `web/vite.config.js` 的 `base` 必须是**相对路径 `'./'`**：写死 `/siyige/v2/` 本地直连白屏，写死 `/v2/` 线上 404
- 用浏览器 Network 面板看第一个红的是 `…/assets/index-xxxx.js` 还是 `/siyige/siyige/v2/…`（后者说明前缀被拼了两次，反代 + base 各加一次）
- 临时改用绝对前缀验证：`$env:VITE_BASE='/siyige/v2/'; npm run build`（验证完记得回滚成相对路径再提交）

**④ 都没问题时** 再看应用侧：`docker compose exec server env | findstr SPRING` 有没有误配 `SERVER_SERVLET_CONTEXT_PATH`（容器里应为空，前缀由反代负责），以及 `JwtAuthFilter` 里 `/siyige` 前缀剥离逻辑是否和实际反代行为一致。

三条约定：

1. **不是运行期依赖**。后端 jar、前端产物、Docker 镜像、CI 都不引用这些文件（`.dockerignore` 已把 `scripts/_*`、`scripts/verify_*.mjs` 排除在构建上下文外）；删掉它们不影响线上，但会丢历史修复上下文和复现步骤。
2. **不要随意删除**。命名再乱、看起来再「一次性」，也可能是某个线上问题的唯一复现脚本；真要清，先确认没被 `.github/workflows/`、`docs/*.md`、`package.json` 引用，且最近没人跑过。
3. **归档到 `scripts/archive/` 需要单独评审**：单独 PR、先改引用（docs / README / CI）、`git mv` 保留历史（不删只移），并说明「归档后哪些还能跑、怎么跑」。运维侧的 `predeploy_check.sh`、`scripts/ops/*.ps1`、`smoke_routes.mjs`、`scripts/dev/` 不进 archive。

## 上线前必须做的 5 条检查

1. `server/config/application.yml` 就位且是**线上值**：`siyige.redis.enabled: true`、`pace.time-scale: 1.0`、`pay-secret` 已换、LLM key 有效；该文件不进镜像、不进 git。
2. CI 全绿：后端 `mvn -B test` 无失败、前端 node 20/22 构建通过且 `static/v2` 产物与仓库一致（有 diff 就先本地 build 再提交）。
3. 升级前跑 `scripts\ops\backup.ps1`，确认 `backups\` 里生成了当次 zip（H2 文件库模式尤其必须）。
4. 用**新 tag** 构建并 `docker compose up -d`，`docker compose ps` 两服务都 `healthy`；`scripts\ops\healthcheck.ps1` 退出码为 0。
5. 从**公网入口**验一遍：`/siyige/api/health`、`/siyige/v2/index.html`、`/siyige/` 都 200，页面冒烟 `smoke_routes.mjs` 全绿；上一版 tag 保留好以便一条命令回滚。
