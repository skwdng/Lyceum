# 本迭代完善计划 · Lyceum 思弈阁（2026-11-27 → 2026-12-10）

> **一迭代 = 两周**。本文只写能验证的东西：每项都有 **负责人 / 依赖 / 验收命令或可观察结果 / 风险**。
> 角色定义与编制口径见 [团队编制与验收.md](团队编制与验收.md)；产品边界见 `README.md`「产品边界」（核心做深、生态冻结）。
>
> 迭代起止：**2026-11-27（周五）需求冻结** → **2026-12-10（周四）验收归档**，10 个工作日 + 2 个半天（周会 / 演示）。

## 0. 迭代边界（先说清楚不做什么）

| 做 | 不做 |
|---|---|
| 让「评分可解释」与「AI 不说假话」这两件影响训练可信度的事落地 | 不加新功能（社区 / 视频 / 好友 / 管理台**冻结，只修 P0 缺陷**） |
| 补 CI 门槛与容器化，把质量从「靠人记得跑」变成「流水线跑」 | 不换技术栈（Java 17 + Spring Boot 3 + Vue 3 + Vite 6 + DeepSeek 保持） |
| 评测集扩容 + 护栏指标，让「改好了还是改坏了」有判据 | 不做 H2 → MySQL 迁移（`docs/migration-mysql/` 本迭代只出评审意见） |
| 设计 tokens 与复盘口径面板，把「为什么是这个分」摆在用户面前 | 不做观战模式、赛后一键发帖、通知实时推送（[项目进度](项目进度.md) §还没做的，均为 P2） |

**容量核对**：8 人 × 10 工作日 ≈ **80 人日**；本迭代 8 项合计约 **32 人日（40%）**，
其余 48 人日留给线上问题、评审会、联调返工与缓冲。若本迭代实际占用 >70%，下一迭代按
[团队编制与验收](团队编制与验收.md) §12 提加人（优先第二个后端 / 前端）。

## 1. 优先级判定口径（避免每次开会重新吵）

| 级别 | 判据（满足任一即是） | 处理 |
|---|---|---|
| **P0** | ① 影响「练了有没有用」的可信度（评分口径、AI 假引用）；② 影响线上可用性（CI 守住回归、部署可复现）；③ 用户能直接看到且会因此不信任产品 | 本迭代必须完成，未完成则迭代失败 |

| **P2** | 有工时再做（训练前后 A/B、AI 评审团补维度、观战模式） | 只登记，不排期 |

## 2. 八项工作（逐项：负责人 / 依赖 / 验收 / 风险）

### ① 评分口径可解释：rubric + 证据 + 优先改进 —— **P0**

- **负责人**：后端（`ScoreService` 字段）+ 前端（`ReviewView` 展示）；PM 定文案口径。
- **依赖**：⑦ 顾问 rubric-v3 草案（D3 出，文案才敢定稿）；①的后端字段是 ④ 的前置。
- **做法（真实文件）**：
  - 后端 `server/src/main/java/com/siyige/service/ScoreService.java`：`Score` record 增加每个维度的**可解释明细**
    （`baseline` / 命中项标签 / 加扣分数值），把现有正则（`JUDGE / STANDARD / CAUSAL / CONCEDE / QUESTION / PRECISION / SLOGAN`）
    的命中结果从「只影响分数」变成「同时输出理由」；新增 `priorityFix`（按 `权重 × (100-维度分)` 排序取第一条）。
  - 证据侧复用 `EvidenceService.audit`（已有 `cited` / `fabricated`），把「引用了几条卡、编了哪些数字」提到口径面板里。
  - 接口 `api/ApiController.review`：`GET /api/matches/{id}/review` 的 `score` 里新增 `rubric` 与 `priorityFix`，**只加字段不改旧字段**。
  - 前端 `web/src/views/ReviewView.vue`：五维条下面加「为什么是这个分」折叠面板（每维：权重 / 得分 / 命中项 / 规则一句话）；
    同时把 `DIMS` 权重常量与后端收敛到一处（现在 `ReviewView.vue` 写 25/30/15/20/10，`ScoreService` 写 0.25/0.30/0.15/0.20/0.10，**两处硬编码**）。
- **验收（可判定）**：
  ```powershell
  cd server
  mvn -B test -Dtest=ScoreServiceTest+ScoreEvalTest
  # 起服务后对一场打完的对局：
  curl -s http://localhost:8080/api/matches/MATCH_ID/review   # 看 score.rubric / score.priorityFix
  ```
  - 可观察：`score.rubric` 含 5 个维度，每维至少 1 条 reason 文案 + 数值；`priorityFix` 恰好 1 条且指向最低加权维度；
  - 可观察：复盘页每维点开能看到 ≥2 条「你命中了什么」，且与后端返回一致；
  - 回归：`ScoreEvalTest` 四项指标不退化（pairwise ≥1.000 / 合法率 100% / 完整率 100% / 漂移 0）。
- **风险**：`Score` 是 **record**（没有默认参数），加字段会打断所有构造调用点（`ScoreService` 内的 `new Score(...)`、`ScoreServiceTest`、`ScoreHumanAlignTest` 等），漏改直接编译失败 → 缓解：先把新字段放进一个新的 `Score` 定义并保留一个旧的构造器签名（委托给新构造器、新字段给默认值），再逐点替换调用；改完立刻 `mvn -B test` 全量。
- **风险**：面板让复盘页变长（现已 274 行 + 大量内联样式）→ 缓解：默认折叠，移动端单列，交给 ④ 一起做。

### ② AI 引用真实性护栏 + token 预算 —— **P0**

- **负责人**：AI 工程师；后端提供落点，测试出护栏指标。
- **依赖**：无强依赖（可与 ① 并行）；输出喂给 ③ 的护栏指标。
- **做法（真实文件）**：
  - 现状缺口：`EvidenceService.audit` 只作用于**玩家**发言（`ScoreService` 调用），**AI 辩手发言没有护栏**；`AiService` 只有句级去重截断。
  - 护栏：在 `ai/AiService.java` 生成结果落库前插入校验——数字/百分比/年份类 token 必须能在 `EvidenceService.cards(topicId)` 命中，
    否则改写为「需核实」表述或整句替换；命中事件计数随对局落库，接口透出。
  - 预算：按 `Format.stepsOf` 的实际步数 × 单步预算（README 2026-11-21 口径：`1.5k + 1.1k/步`）+ 提示词长度上限；
    超预算时**降级而非失败**（`AiTier.BASIC` 走短提示、跳过第二段分析），`/api/usage` 与 `LlmClient.tokensForMatch` 保持对齐。
- **验收（可判定）**：
  ```powershell
  cd server
  mvn -B test -Dtest=AiServiceGuardTest+AiTierConfigTest
  curl -s http://localhost:8080/api/usage            # 一场之后的累计用量
  ```
  - 可观察：构造 10 条含假数字的样本（"据 2023 年调查 87% 的辩手…"），护栏命中 ≥9 条，且场上文本里不再出现无来源精确数字；
  - 可观察：一场 FULL 的 `tokensForMatch(matchId)` ≤ `1.5k + 1.1k × 步数 × 1.05`；与 `/api/usage` 差值 ≤5%；
  - 可观察：超预算触发降级时日志有一行明确记录（`log.info` 级别，可在 `journalctl` 里 grep 到）。
- **风险**：误伤真实引用（"据教育部 2021 年数据"）→ 缓解：白名单口径 = 论据卡 + 「据/根据 + 年份」模式放行，只拦**精确百分比与虚构统计**。
- **风险**：护栏加一轮校验会拉长时延（两段式已 4–6 s/轮）→ 缓解：护栏做成**本地字符串/规则校验**，不再调一次模型。

### ⑤ CI 补前端与单测门槛 + 容器化 —— **P0**

- **负责人**：运维（0.5，挂平台/全栈）；测试给门槛数字。
- **依赖**：无（可与 ① 并行），但「失败即红」验证要等 ①③ 的用例落地才有意义（D9）。
- **做法（真实文件）**：
  - 现状：`.github/workflows/ci.yml` 三个 job（后端 `mvn test` + `jacoco:report`、前端 `npm run build` + 产物检查、smoke 起 jar 探活）。
    **两个真缺口**：`server/pom.xml` 里**没有 jacoco 插件**（CI 已在调用 `jacoco:report`，注释写「核心模块需 ≥60%」但没有 check 规则）；
    `web/package.json` **没有 test 脚本**，`web/e2e/solo.spec.mjs` 存在但没进 CI。
  - 补：后端加 `jacoco-maven-plugin`（prepare-agent + report + `check`：`service/engine/ai` 行覆盖 ≥60%）；
    前端加 `vitest` + `npm run test`（先覆盖 `stores/debate.js`、`utils/format.js`、`utils/markdown.js` 这类纯函数）；
    e2e 加 job：起服务后跑 `node web/e2e/solo.spec.mjs`（`package.json` 补 playwright 依赖与 script）。
  - 容器化：新增 `server/Dockerfile`（`eclipse-temurin:17-jre` + 沿用 `siyige.service` 的 `-Xmx384m` / SerialGC 参数）
    与 `deploy/docker-compose.yml`（app + redis + 数据卷），systemd 路径保留不删（`server/scripts/siyige.service`）。
- **验收（可判定）**：
  ```powershell
  docker build -f server/Dockerfile -t siyige:dev .
  docker compose -f deploy/docker-compose.yml up -d
  curl -sf http://127.0.0.1:8090/api/health      # {"ok":true}
  bash scripts/predeploy_check.sh                # 五层全 OK（systemd 路径仍可用）
  ```
  - 可观察：PR 上 job 数 ≥4（backend / frontend-build / frontend-test / smoke），**故意让一条断言失败 → PR 变红**（截图留档）；
  - 可观察：`server/target/site/jacoco/index.html` 能打开且 `service/` 行覆盖 ≥60%；
  - 可观察：容器内 `/api/health` 通，`/siyige/v2/index.html` 返回 200 且 >500 B。
- **风险**：1C1G 机器跑 compose（app + redis）内存不够 → 缓解：compose 里给 app `mem_limit: 700m`、redis `maxmemory 128mb`，并保留「不用容器」的 systemd 路线。
- **风险**：CI 时长从 ~8 min 涨到 ~15 min → 缓解：前端 test 与后端 test 并行；jacoco check 只在 `service/engine/ai` 三包上生效。

## 5. DoD（完成定义）：什么叫「这项做完了」

一项工作只有**同时**满足下列 5 条才算 Done，缺一条就是 80%：

1. **代码可跑**：`cd server && mvn -B test` 全绿（用例数 ≥840，不减少）；`cd web && npm run build` 产物落 `server/src/main/resources/static/v2/index.html`。
2. **有回归**：这项涉及的行为至少有 1 个自动化用例或自检脚本覆盖，并**验证过它会红**（故意改坏 → 失败 → 改回 → 绿）。
3. **有证据**：验收报告里贴了命令 + 输出片段（不是「已验证」四个字）。
4. **不退化**：`ScoreEvalTest` 四项指标不降（pairwise ≥0.75 / 合法率 ≥99% / 完整率 ≥98% / 漂移 ≤5）；`scripts/predeploy_check.sh` 五层 OK。
5. **有记录**：`README.md` 更新记录一段（说清「改了什么 / 为什么」）+ [项目进度.md](项目进度.md) 更新记录表一行。

**额外的迭代级 DoD**：
- 本迭代 **5 个 P0 全部 Done**；3 个 P1 至少 Done 2 个，未完成的写明原因与顺延日期。
- **不做 git commit / push**（本迭代纪律）：改动留在工作区，由 Lead 统一评审后再提交。
