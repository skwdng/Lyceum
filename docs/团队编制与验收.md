### 2.4 可兼 / 不可省的理由

编制表标「可兼但会拖慢」。本项目 SPEC 已成文、口径增量小，短期可由后端 lead 兼；
但一旦「口径变更 + 跨端联调 + 版本发布」三件事挤进同一周，兼任会把**决策延迟**直接转成**工期延迟**——
历史证据就在 `README.md` 的 2026-11-09：多轮赛制、充值计费、BYOK、AI 评审团、按席位评分五件事一天内落地，
当天没有任何一份文档同步口径，后续全靠 [辩论侧改动清单.md](辩论侧改动清单.md) 补。

### 2.5 与谁有接口

对全员。接口物是**文档 + 只追加的共享文件**：与后端确认 `review` 返回字段（`score.*`），与前端确认权重常量

### 3.3 验收标准（可判定）

```powershell
cd server
mvn -B test -Dtest=TurnEngineTest+MatchServiceTest+MatchReaperTest+ScoreServiceTest+FlawServiceTest+FormatTest
```

除「全绿」外，必须能逐条指认：

- **B1 赛制不重不漏**：FULL 模式（q=2/f=4）步号 1..18 连续、每步席位 ∈ `SEATS`、`turnsOf` 与步骤表一致（`TurnEngineTest` / `FormatTest`）。
- **B2 幂等**：同一 `step` 重复提交只生效一次；`/skip` 连点不产生两条推进（`MatchServiceTest` / `scripts/verify_nudge_once.mjs`、`verify_dupe_click.mjs`）。
- **B3 越权**：非 owner 或非同房间席位访问 `/api/matches/{id}`、SSE、`/turns`、`/skip`、`/buzz` 一律 403（`MatchAccessTest`、`JwtAuthFilterDebateScopeTest`）。
- **B4 僵尸回收**：`deadline_at` 是 `Timestamp` 时 anchor 也能取到（2026-11-21 修过的真 bug，必须有回归用例 —— `MatchReaperTest`）。
- **B5 端到端**：`node scripts/verify_full_run.mjs http://localhost:8080` 从开局跑到复盘出数。
- **B6 并发不崩**：`node scripts/probe_match_state.mjs` 观察 5 场并发时单轮间隔 ≤ 6 s（README 2026-11-21 基线：串行几十秒 → 4–6 s）。

### 3.4 为什么**不可省**

编制表原文如此，本仓库证据也支持：引擎是纯函数（可单测），但**编排不是**——`MatchService` 884 行、
`AiService` 884 行，两者共享 in-flight 集合与 `tick` 时序。两个真实事故都长在这一层，且都是「前端看不出来、
不写测试就永远不知道」的类型：
① 僵尸回收从未生效（`num()` 只认 `Number`，`deadline_at` 是 `Timestamp`，anchor 恒 0）；
② `parseSeats` 空值默认 `{A1}`，房间反查席位时会把提交者当成 A1，**替别人发言**（新增 `parseSeatsStrict` 修掉）。
这一席没人，等于把「对局能不能推进、钱扣得对不对」交给运气。

### 3.5 与谁有接口

- 对前端：`/api/matches/*` 的字段与 SSE 事件体（`since` 游标语义）；`review` 的 `score / seatScores / panel / billTokens`。
- 对 AI：`AiService` 是 `MatchService.tick` 的被调方，必须幂等、必须按 `matchId` 归集 token（`LlmClient.tokensForMatch`）。
- 对测试：可测性（`tick` 可手动驱动、`siyige.pace.time-scale` 可缩放时间）。
- 对平台：`community/` `social/` 只经 `ApiController` 与 admin 权限点接触，不直接改后端编排。

### 4.3 验收标准（可判定）

```powershell
cd server
mvn -B test -Dtest=AiServiceGuardTest+AiTierConfigTest+AiPromptBuilderTest+AiUsageGuardTest
mvn -B test -Dtest=ScoreEvalTest        # 改提示词/评分后必须跑，这是"变好还是变坏"的判据
```

- **C1 预算**：一场 FULL 的实际 token ≤ 估算上限（口径 = `1.5k + 1.1k × 步数`，见 README 2026-11-21「费用预估按赛制动态」）；
  `curl -s http://localhost:8080/api/usage` 与 `tokensForMatch(matchId)` 差 ≤5%。
- **C2 引用真实性护栏**：AI 辩手发言里出现的数字，要么能在 `EvidenceService.cards(topicId)` 命中，要么被标「需核实」/被改写；
  用 10 条含假数字的构造样本回归，命中率 ≥90%（本迭代新增断言，见计划 ②）。
- **C3 时延**：单轮首字 ≤2 s、整轮 ≤8 s（2026-11-21 基线：首字 1.6 s、定稿 378 字不重打）。
- **C4 评审团不塌**：4 位裁判独立 → 平均分区间 `min/max` 有差；共识项只收 ≥2 位提到的问题（`AiJudgeService` 既有语义，需有单测锚定）。

### 4.4 「可兼但会拖慢」的真实含义

编制表写「可兼」。本项目现实是：提示词改一行就可能让 `ScoreEvalTest` 的 pairwise 从 1.000 掉下来
（[评分有效性评测报告](评分有效性评测报告.md) §4 记的三次翻车全部来自「规则/提示词微调」）。
兼任等于「改完没人跑评测」。若必须兼，最低纪律：**任何 `prompts/` 或 `AiService` 关于内容的改动，必须附一次 `ScoreEvalTest` 输出**。

### 4.5 与谁有接口

对后端（被 `tick` 调用，幂等 + 归集 token）；对前端（流式 token 事件默认**关闭**，开 `siyige.ai.stream` 才推）；
对测试（评测集与护栏指标）；对顾问（提示词里的判准话术必须和 rubric 一致，否则「评分说你好、AI 说你差」）。

- **I3** 重启不丢数据：确认 H2 是 file 模式（`jdbc:h2:file:...`）；若走内存模式，必须在自检里**标红**并在文档写明（[项目进度](项目进度.md) §还没做的：「管理员改密重启会回滚」就是这个坑）。
- **I4** CI 三 job 全绿且**失败即红**（故意让一个断言失败验证一次，截图留档）；覆盖率数字真实产出（补 jacoco 插件后 `target/site/jacoco/index.html` 可打开）。
- **I5** 事故口径：`journalctl -u siyige --since "-10 min" | grep -c ERROR` 为 0。

### 10.4 为什么「出事故最痛」在本项目成立

本项目的事故形态非常具体，而且**全都只有运维视角能提前发现**：
① 8787 反代块丢失 → 整站 404（`predeploy_check.sh` 第 4 层就是为它写的）；
② 2C1G/1C1G 上 `-Xmx384m` 打满 → OOM，进程被 `MemoryMax=700M` 砍掉；
③ Redis 挂了 → 社区浏览、热榜、未读、AI 队列一起失效（代码里有一堆 `InMemory*` 兜底实现，兜底是否生效只有线上能验）。
这 0.5 个人买的是「上线十分钟内发现问题」的能力。

对后端（启动参数、健康检查、日志、配置开关）；对平台（Redis 硬依赖、Lua 脚本）；对 PM（上线窗口与回滚预案）；对测试（CI 门槛）。

## 12. 编制不足时的降级顺序（给老板的取舍清单）

| 2 | 顾问降为月度评审 | 0.5 | rubric 停在 v2，评分「自洽但不贴人」的问题无法被发现 | 测试兼（自我一致） |
