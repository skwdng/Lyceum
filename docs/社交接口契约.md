# 社交接口契约（好友 + 私聊 + 邀请组队）

> 版本：v1（2026-11-07）。对应 `docs/SPEC.md` §23（R-SOC-01 ~ R-SOC-20）。
> 前缀一律 `/api/social/**`；WebSocket 在 `/ws/chat`。
> 本文是这一块的**唯一口径**：字段名、错误码、未读语义、WS 帧格式都在这里定死。

---

## 0. 上手三分钟（如果只读一段）

1. **只有好友能私聊**。非好友发消息 → `403 NOT_FRIEND`。删好友后历史还在，但发不出去。
2. **未读数在 Redis，不在数据库**。数据库只存「读到哪条」（`read_a`/`read_b`）。
   角标和会话列表的数字走缓存，**不查库**；只有冷启动和进会话列表时才回源校准。
3. **消息一定送达，但可能延迟**。WebSocket 断了就用 `afterId` 补拉，一条都不会丢。
   线上没改 Nginx 之前会自动降级成 3 秒轮询，**收发都还能用**。

## 1. 鉴权

| 项 | 规则 |
|---|---|
| 传输 | 请求头 `Authorization: Bearer <jwt>`（与社区/辩论侧一致） |
| WebSocket | 查询参数 `?token=<jwt>`（浏览器 WS 不能自定义请求头） |
| 未登录 | 所有 `/api/social/**` 一律 `401 UNAUTHORIZED`，**读也一样** |
| 管理员令牌 | `401 NOT_ADMIN`（管理员不能以用户身份用社交接口） |
| 黑名单 | 退出登录后的 jti 立刻失效（HTTP 与 WS 都拦） |

> `/ws/**` **不注册任何 Servlet 过滤器**。握手鉴权在 `ChatHandshakeInterceptor` 里做。
> 把 WS 塞进 `JwtAuthFilter` 会破坏「`?token=` 只对 `/events` 回退」这条既有规则。

## 2. 接口一览（12 个）

| # | 方法 · 路径 | 请求 | 返回 | 状态码 |
|---|---|---|---|---|
| 1 | GET `/api/social/users?q=` | `q` 必填（账号/昵称片段） | `{items[],total}`，最多 10 条 | 200 |
| 2 | POST `/api/social/friends/requests` | `{toId, note?}` | `{status:'PENDING'\|'ACCEPTED', requestId, toId}` | 200 / 400 / 403 / 404 / 409 |
| 3 | GET `/api/social/friends/requests` | —— | `{items[],total}`（我收到的 PENDING） | 200 |
| 4 | POST `/api/social/friends/requests/{id}/accept` | —— | 无 body | 204 / 403 / 404 / 409 |
| 5 | POST `/api/social/friends/requests/{id}/reject` | —— | 无 body | 204 / 403 / 404 / 409 |
| 6 | GET `/api/social/friends` | —— | `{items[],total}` | 200 |
| 7 | DELETE `/api/social/friends/{userId}` | —— | 无 body | 204 / 403 / 404 |
| 8 | GET `/api/social/conversations` | —— | `{items[],total,unreadTotal}` | 200 |
| 9 | GET `/api/social/messages?convId=&beforeId=` | 向上翻页 | `{convId,peer,items[],hasMore,myRead}` | 200 / 400 / 403 / 404 |
| 10 | GET `/api/social/messages?convId=&afterId=` | 断线补拉 | `{convId,items[],hasMore}` | 200 / 400 / 403 / 404 |
| 11 | POST `/api/social/messages` | `{toId, body}` 或 `{toId, type:'INVITE', roomCode, topicTitle?}` | 落库后的消息 | 200 / 400 / 403 |
| 12 | POST `/api/social/conversations/{id}/read` | `{lastMsgId?}` | `{convId,lastMsgId,unread}` | 200 / 403 / 404 |
| 13 | GET `/api/social/unread-count` | —— | `{unread}` | 200 |

> 表里 13 行：任务书列了 10 个，**`POST /messages` 与 `GET /unread-count` 是额外加的**，理由见 §5.1 与 §6.1。

### 2.1 关键字段

```
用户条目（搜索/好友）  {id, name, isBot, isFriend, hasPendingRequest, pendingIn, isSelf}
                       —— 三个布尔由**后端**算，前端不许自己推断按钮该画什么
待处理请求             {requestId, fromId, fromName, note, createdAt}
会话行                 {convId, peer:{id,name,isBot}, last:{id,fromMe,preview,type}|null, unread, lastMsgAt}
消息                   {id, messageId, convId, fromId, toId, type, body, payload, createdAt}
                       —— id 与 messageId 同值：HTTP/ack 用 messageId，WS 帧里叫 id
INVITE payload         {"roomCode":"SY-8F3K","topicTitle":"...（≤60 字）"}
```

时间一律 **epoch 毫秒**；字段名 camelCase；表名 `sy_` 前缀且只在 `schema-social.sql` 里建。

## 3. 错误码

错误体固定 `{"code":"...","message":"..."}`（`SocialErrors` 只对 `SocialController` 生效）。

| code | HTTP | 场景 |
|---|---|---|
| `INVALID_PARAM` | 400 | 参数缺失 / 类型不对 / `beforeId` 与 `afterId` 同时传 |
| `INVALID_TARGET` | 400 | 收件人为空或等于自己 |
| `INVALID_BODY` | 400 | 消息为空 |
| `BODY_TOO_LONG` | 400 | 单条消息 > 2000 字（按**码点**算） |
| `INVALID_ROOM_CODE` | 400 | 房间号不是 `SY-` + 2~10 位大写字母数字 |
| `CANT_ADD_SELF` | 400 | 加自己为好友 |
| `TARGET_IS_BOT` | 400 | 加 AI 账号为好友 |
| `NOT_FRIEND` | 403 | 不是好友（发消息 / 发邀请） |
| `NOT_MEMBER` | 403 | 不在该会话里 |
| `NOT_REQUEST_TARGET` | 403 | 这条好友请求不是发给我的 |
| `NOT_ADMIN` | 401 | 管理员令牌打社交接口 |
| `USER_NOT_FOUND` | 404 | 用户不存在 |
| `REQUEST_NOT_FOUND` | 404 | 请求不存在 |
| `CONV_NOT_FOUND` | 404 | 会话不存在 |
| `ALREADY_FRIEND` | 409 | 已经是好友 |
| `PENDING_EXISTS` | 409 | 同方向已有待处理请求 |
| `REQUEST_NOT_PENDING` | 409 | 请求已处理过 |

### 3.1 几条容易踩的语义

- **附言超 100 字：静默截断**，不报错（决策 6）。按码点截，中文不会被切坏。
- **被拒绝后可以重新发**，旧的 `REJECTED` 行保留不挡路；只有同向 `PENDING` 才 `409`。
- **双向互发自动成为好友**：两条请求都置 `ACCEPTED`，双方各收一条 `FRIEND_ACCEPTED`。
  不这么做会出现「两边都显示已发送、谁也没法接受」的死局。
- **拒绝不通知**发起人（避免骚扰），只有接受才通知。
- **AI 账号（`is_bot=1`）三重拦截**：搜索不返回、加好友 400、不能私聊。
- **本期没有任何频率限制**（原「20 条/分」「10 次/天」）：**2026-11-07 经产品确认不做**。
  若将来要加，请在网关/过滤器层做，不要塞进 `ChatService`（会把事务与限流耦在一起）。

## 4. 好友的两处数据设计（为什么这么建表）

**字典序成对**：`sy_friend(user_a, user_b)` 主键，写入前按字典序排好。好处：
- `(A,B)` 与 `(B,A)` 只有一行 → 删除时不可能「只删了一边」，也就不会出现单边好友
- 查好友列表时 `case when f.user_a = ? then f.user_b else f.user_a end` 一把捞出来

**请求表留全生命周期**：`PENDING / ACCEPTED / REJECTED` + `handled_at`。
被拒绝的那条不删，是为了「为什么没加成」有据可查；同时不挡新请求。

## 5. 消息与分页

### 5.1 为什么除了 WebSocket 还有 `POST /messages`

决策 2 要求：线上没改 Nginx 之前，靠轮询也要能把聊天跑起来。
但轮询只能「收」——发不出去整条链路就是半残。所以 HTTP 发送是**兜底通道**，
前端在 WS 不可用时自动走它，用户完全无感。

**WebSocket 与 HTTP 共用同一个 `ChatService.send`**：换传输方式时业务层一行不用改。

### 5.2 两个游标，各管一件事

| 参数 | 用途 | 排序 | 说明 |
|---|---|---|---|
| `beforeId` | 向上翻历史 | 倒序取 20 条 → 前端反转为正序 | **不用 offset**：翻页时新消息可能正在进来，offset 会错位 |
| `afterId` | 断线补拉 / 轮询 | 正序，`id > afterId` | 一次最多 200 条；`hasMore=true` 就继续拉 |

两者**不能同时传**（`400 INVALID_PARAM`）：前端写错时不该悄悄拿到不想要的数据。

### 5.3 消息生命周期

1. 校验：收件人存在且不是自己 → 好友关系 → 内容非空且 ≤2000 字
2. 打码：`SensitiveWordMasker` 逐码点替换为全角＊，**原文不落库**
3. 落库：`sy_direct_message` 插一行；`sy_conversation` 的 `last_msg_id` 跟上
4. 已读位置：**发件人自己**的 `read_a/read_b` 推到这条（否则自己的消息在自己这边显示未读）
5. 未读：收件人 Redis `+1`
6. 推送：推给收件人的**所有连接** + 发送方的其它端（多端一致，前端按 id 去重）

消息**永不清理**（决策：不做保留期）。

## 6. 未读：缓存是读路径，数据库是真相

### 6.1 为什么 `GET /unread-count` 是必需的

侧栏「消息」角标每 30 秒要问一次「我总共几条没读」。如果这也要拉整个会话列表，
一旦上 MySQL，每次轮询就是一次真实查询——Redis 那套就白做了。
所以单独给一个**只读缓存**的接口：一次 `HGETALL`，零数据库查询。

### 6.2 数据结构

```
Redis Hash  social:unread:{userId}
  field = convId     value = 该会话未读条数
  field = "_"        value = 0（哨兵，只用来标记「初始化过」）
```

- **侧栏角标** = 所有 field 求和
- **会话列表每行** = 该 convId 的 field
- 空 Hash 也写哨兵：否则「没有未读」会被反复判成冷缓存，把查询又带回轮询路径

数据库的 `read_a` / `read_b` 存「读到哪条消息 id」，用途只有两个：
① 算这次标已读**实际读掉几条**；② 缓存丢了按库重建。

### 6.3 三条写路径

| 触发 | 动作 |
|---|---|
| 发消息 | 收件人该会话 `HINCRBY +1` |
| 标已读 | 先一条 SQL 算区间 `(旧位置, 新位置]` 内非我发的条数，再 **Lua 原子递减**（减到 ≤0 删 field） |
| 冷启动 / 进会话列表 | 一条聚合 SQL 全量重建（先 `DEL` 再 `HSET`，避免残留已删会话） |

**为什么递减要用 Lua**：`HGET` 出来减再 `HSET` 是三步非原子，多端同时标已读会互相覆盖
（典型现象：角标减到 0 又跳回 2）。

**为什么不能一律 `-1`**：用户可能一次滚动读掉了 20 条。

### 6.4 一致性

已读位置只**前进**（`greatest(coalesce(col,0), ?)`）：迟到的旧回执不会把已读打回去。
多端一致靠「同一份缓存」：手机标了已读，电脑端下一次问角标就是 0。

### 6.5 Redis 不可用时

未读相关操作全部 catch 后 warn，**不影响发消息**（消息已落库）。
读不到按 0 处理；下一次进会话列表会按库自愈。
没有 Redis 的开发环境用 `InMemorySocialUnreadCounter`（`siyige.redis.enabled=false`），
语义与 Redis 版逐条对齐。

## 7. WebSocket 协议

### 7.1 连接

```
URL      ws(s)://<host>/ws/chat?token=<jwt>
鉴权失败 握手直接失败（浏览器 onerror / onclose），前端显示「请重新登录」并降级轮询
```

握手前校验：令牌可解析 → 未过期 → 不是管理员令牌 → jti 不在黑名单。
通过后把 `userId` 放进 session attributes（WS 没有 RequestContext，这是唯一途径）。

### 7.2 帧格式（JSON，`type` 区分）

客户端 → 服务端：

```json
{"type":"send","toId":"bob","body":"在吗","clientMsgId":"c-abc1"}
{"type":"read","convId":7,"lastMsgId":103}
{"type":"ping"}
```

服务端 → 客户端：

```json
{"type":"ack","clientMsgId":"c-abc1","messageId":104,"convId":7,"createdAt":1794025603008}
{"type":"msg","message":{"id":104,"convId":7,"fromId":"bob","type":"TEXT","body":"在吗","payload":null,"createdAt":1794025603008}}
{"type":"read","convId":7,"lastMsgId":104}
{"type":"pong"}
{"type":"error","code":"NOT_FRIEND","clientMsgId":"c-abc1"}
```

- `ack` 一定带回 `clientMsgId`，前端才能把「发送中」气泡翻成已发送
- `error` 也带 `clientMsgId`（有的话），前端把那条气泡标成「发送失败」而不是永远转圈
- **业务拒绝不关连接**：只有传输层出错才断开
- 一条消息会推给收件人的**每一个**连接（手机+电脑同时在线），也推给发送方的其它端

### 7.3 连接管理（前端 `js/chat-ws.js`）

| 项 | 值 | 理由 |
|---|---|---|
| 心跳 | 25 秒 `ping` | 小于 Nginx 默认 60 秒空闲超时，不会被动掐断 |
| 假死判定 | 上一轮没收到 `pong` 就主动断开重连 | 网络切换后连接常处于「假活」状态 |
| 重连退避 | 1→2→4→…→30 秒封顶 | 抖动时不会把服务端打满 |
| 重连补拉 | 按当前会话 `afterId` 拉一次 | 断线期间的消息一条不落 |
| 降级阈值 | **连续失败 3 次** | 再等下去用户体验崩了 |
| 降级后 | 每 **3 秒** 轮询 `afterId` + `unread-count` | 延迟 ≤3 秒 |
| 恢复 | WS 一连上就停轮询并切回实时 | 无需手动刷新 |

`chatWsMode()` 返回 `live` / `polling` / `connecting`：`state` 在重连过程中会闪，
**外部判断请用 `chatWsMode()`**。

## 8. 邀请组队（INVITE）

- INVITE 是**消息的一种 type**，不是新表。好处：好友校验、建会话、未读、推送、
  历史分页、离线补拉全部自动复用。
- 只有**房主**能邀请（队友自己拉人容易出现「房间被塞满、房主不知道」）。
- 房间号格式 `SY-` + 2~10 位大写字母数字；后端统一转大写，格式不对 `400`。
- 辩题标题超过 60 字截断（卡片放不下）。
- 接收方点卡片上的「加入房间」直接走 `POST /api/rooms/{code}/join`
  —— 与手动输房间号**同一条路径**，不特殊。

## 9. 上线前置条件（Nginx）

线上若前面有 Nginx / 反代，**必须补下面这段**，否则 WebSocket 连不上
（会自动降级成 3 秒轮询，功能可用但延迟变高）：

```nginx
# WebSocket 升级（放在 /siyige 的 location 内）
location /siyige/ws/ {
    proxy_pass http://127.0.0.1:8080/ws/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 300s;      # 必须 > 心跳 25s，否则空闲连接会被掐
    access_log off;               # 令牌在 URL 里，别落日志
}
```

**若严格要求「不改 Nginx 也能聊」**，则本方案的降级链路已满足：
WS 连不上 → 自动 3 秒轮询 → 收（`afterId`）与发（`POST /messages`）都正常。

## 10. 表结构（`schema-social.sql`）

```sql
sy_friend(user_a, user_b, created_at, PK(user_a,user_b))                       -- 字典序一行
sy_friend_request(id, from_id, to_id, note, status, created_at, handled_at)
sy_conversation(id, user_a, user_b, last_msg_id, last_msg_at,
                read_a, read_b, created_at, unique(user_a,user_b))
sy_direct_message(id, conv_id, from_id, to_id, type, body, payload, created_at)
```

索引：
- `sy_friend(ix_friend_b)`
- `sy_friend_request(ix_freq_to)`、`(ix_freq_from)`
- `sy_conversation(ix_conv_last)`
- `sy_direct_message(ix_dm_conv)` — `(conv_id, id)`，历史分页与补拉都吃它

四张表**全在 `schema-social.sql`**，不动任何既有 schema 文件。

## 11. 不做什么（本期明确排除）

- 不做频率限制（见 §3.1）
- 不做拉黑 / 屏蔽
- 不做在线状态、正在输入
- 不做消息撤回、编辑、删除
- 不做群聊（只有一对一）
- 不做语音/图片/文件（只有 TEXT 与 INVITE 两种 type）
- 消息永不清理
