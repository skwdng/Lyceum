# MySQL 切库操作手册（把默认库从 H2 换成 MySQL）

> 适用：`dev-mysql` 分支（已备好 mysql profile、全量 schema、两套 schema 守卫、测试钉回 H2）。
> 目标：某天用正式操作把 `application.yml` 的默认数据源切成 MySQL，并**可回退**。
> 现状：默认仍是 H2；MySQL 只在 `-Dspring-boot.run.profiles=mysql` 下使用。

---

```text
演练备份 → 停服 → 大盘备份 → 改 application.yml → 起服务 → 冒烟 → 观察 → （不行就回滚）
```

## 2. 时区：**最容易踩的坑**

```text
容器里的 MySQL 默认 UTC。应用写的是本地时间，两边混在一张表里就差 8 小时：
sy_match.started_at（DB 的 default current_timestamp）与 deadline_at（应用写入）会差 8h，
表现是对局倒计时直接算错、tick 不推进或立刻超时。

必须二选一：
  A. 连接串里钉住：connectionTimeZone=%2B08:00 + hikari.connection-init-sql=SET time_zone='+08:00'
     （application-mysql.yml 就是这么做，用数字偏移而不是 Asia/Shanghai ——
      容器里没装 MySQL 时区表，命名时区会 SET 失败）
  B. 给 MySQL 装上时区表后，服务器端 default-time-zone='+08:00'
```

## 3. 备份 / 还原（脚本已就绪并演练过）

```powershell
# 备份（自动时间戳，只留最近 7 份；--single-transaction 不锁表，服务可不停）
.\server\scripts\backup_mysql.ps1

# 只看当前库状态（表数 + 几张表的行数）
.\server\scripts\backup_mysql.ps1 -Verify

# 还原（脚本会先给当前库拍一份再还原）
.\server\scripts\backup_mysql.ps1 -Restore D:\siyige-v2\_backup\siyige-auto-20261127-221728.sql
```

2026-11-27 演练记录（真做过，不是设想）：

```text
1. 造 3 条数据（标签/屏蔽词/参数）
2. 备份：41.4 KB / 42 张表
3. drop table sy_alert_mute  ->  表数 42 -> 41，该表消失
4. -Restore 还原  ->  表数回到 42
5. 验证：sy_alert_mute 回来了、3 条数据一条不少
```

> 附带结论：脚本里有一条「备份文件里没有 CREATE TABLE 就报错」的守卫。
> 2026-11-27 库被外部清空时，正是它把「空备份」拦下来了（否则会写出一份 1.5KB 的假备份）。

## 4. 切换步骤（逐条执行，每条都有预期输出）

### 4.1 停服前：备份 + 记录基线

```bash
# 1) 先备份当前 MySQL（如果已经在用），或至少备份要保留的数据
.\server\scripts\backup_mysql.ps1

# 2) 记录当前基线，切完要对比
.\server\scripts\backup_mysql.ps1 -Verify     # 表数 + 各表行数
```

### 4.2 改配置（只改这两处）

```yaml
# server/src/main/resources/application.yml
spring:
  datasource:
    url: jdbc:mysql://<host>:3308/siyige?useUnicode=true&characterEncoding=UTF-8&connectionTimeZone=%2B08:00&allowPublicKeyRetrieval=true&useSSL=false
    username: ${SIYIGE_DB_USER:root}
    password: ${SIYIGE_DB_PASSWORD:siyige123456}
    driver-class-name: com.mysql.cj.jdbc.Driver
  sql:
    init:
      mode: always
      schema-locations: classpath:schema-mysql-full.sql   # 16 个 H2 文件换成这一个
```

```text
注意：
  · 16 个 schema-*.sql 是 H2 方言，MySQL 下会直接语法错，所以 schema-locations 必须只剩一个文件
  · hikari.connection-init-sql 那条时区语句要一起搬过来（见 §2）
  · 不要删 H2 的依赖与那 16 个文件 —— 单测还在用（见 §5）
```

### 4.3 起服务

```bash
mvn -q -DskipTests spring-boot:run          # 不再需要 -Dspring-boot.run.profiles=mysql
```

预期日志：`HikariPool-1 - Start completed`；无 ERROR；
```bash
curl http://127.0.0.1:8080/api/health          # 200
```

### 4.4 建表与种子（**没有数据迁移这一步**）

> H2 是内存库（`jdbc:h2:mem:siyige;DB_CLOSE_DELAY=-1`），运行时数据不落盘、重启即空，
> 仓库里也没有任何 `*.mv.db` 业务数据文件。所以切库**不存在「把老数据导过来」这件事** ——
> 切过去看到的所有内容都由种子产生：
>
> | 谁灌的 | 灌什么 |
> |---|---|
> | `AdminSeeder` | 管理员（仅在没有任何管理员时） |
> | `DataSeeder` / `Store` | 12 个辩题 |
> | `EvidenceSeeder` | 48 条论据 |
> | `WordBootstrap` | 三份屏蔽词（7 / 7 / 6） |
> | `VideoSeeder` | 演示视频 |
>
> 唯一写在 SQL 里的种子是 `schema-admin.sql` 的那条 `insert into sy_admin`（H2 用）；
> MySQL 侧靠 `siyige.admin.seed.*` 配置，**生产要关掉或改强密码**（见 §4.2 的提醒）。
### 4.4 建表与种子

```text
· schema-mysql-full.sql 全部 create table if not exists，重复执行安全
· 空库首次启动会自动：AdminSeeder（admin/admin123，仅当没有任何管理员）、
  WordBootstrap（导入种子屏蔽词）、ConfigKey 默认值（不需要落库）
· 确认：表数 42；sy_admin 至少 1 行；sy_sensitive_word 7/7/6
```

### 4.5 冒烟（按顺序，全绿再往下）

```bash
node scripts/selftest_mysql.mjs        # 44 条功能回归
# 关键一条：房间对局要能自己推进（不能用默认 solo，solo 不限时本来就不推进）
curl -X POST .../api/matches -d '{"mode":"FULL","seats":["A1","B1"],"topicId":"t3","kind":"room"}'
```

### 4.6 观察（建议 24-48 小时）

| 看什么 | 正常表现 | 出问题先查 |
|---|---|---|
| 对局能否推进 | tick 正常，无 ClassCastException | §2 时区 |
| 登录 / 令牌 | 200，角色正确 | Redis 是否连上 |
| 社区发帖 | 打码生效、标签计数对 | 屏蔽词表是否导入 |
| 报表数字 | PV/UV/DAU 有数、日期对 | 时区 + day_key 生成 |
| 钱包 | 开局扣费、结算多退少补 | 并发（见 README §7） |
| 慢查询 | 列表页 < 500ms | 索引是否被丢 |

## 5. 回滚预案

```text
情况 A：刚改完起不来 / 冒烟大面积失败
  → git checkout server/src/main/resources/application.yml   （一行就回到 H2）
  → 重启。H2 是内存库，重启即空库，但**服务立刻可用**。

情况 B：跑了一阵发现数据错乱
  → 用 §3 的 -Restore 回到切换前的备份；
  → 如果备份也救不了，只能回 H2，代价是 MySQL 期间的增量数据丢失；
  → 所以切换前必须明确：**这段时间允许丢多少数据**。

情况 C：库被误删（真实发生过，见 §6）
  → 停服 → 用最近备份 -Restore → 起服务 → 确认表数 42 与关键表行数
```

## 6. 真实事故记录：库被清空

```text
2026-11-27 一次 QA 全量测试开始时按流程执行了：
  redis-cli FLUSHALL + MySQL  DROP DATABASE siyige; CREATE DATABASE siyige
（见 D:\siyige-v2\QA-测试报告-2026-11-27.md 第 7 行）

结果：42 张表变 0，且当时没有任何备份 —— 数据不可恢复。
教训：
  1) 任何「清空重来」的操作之前，必须先跑一次 backup_mysql.ps1；
  2) 备份脚本「空备份要报错」的守卫是对的（当时正是它拦下了 1.5KB 的假备份）；
  3) 生产上更要禁止这种「一键清库」，改成「建新库 + 导数据 + 切连接」。
```

## 7. 切换之后，H2 还剩什么用

| 用途 | 说明 |
|---|---|
| 单测 | 828 个用例跑在 `application-test.yml`（H2）上，**永不删** |
| `SchemaParityTest` | 用 H2 跑 16 个文件，与 MySQL 全量 schema 比对 |
| 临时验证 | 想快速试一段 SQL，不用动 MySQL |

也就是说：**H2 不会消失，它退化成测试专用**；生产上由 MySQL 取代它。

## 9. 加列 / 加索引型变更怎么上线（没有 Flyway 时的唯一套路）

切库之后最容易踩的坑不是切库本身，而是**之后改表**：`schema-mysql-full.sql` 里全是
`create table if not exists`，它对**已存在的表一个字段都不会加**。

2026-11-28 的实例：`sy_user` 加 `phone`，本地库刚好手工 ALTER 过所以看不出问题，
一旦部署到生产（库早就建好了）就是：

```text
java.sql.SQLSyntaxErrorException: Unknown column 'phone' in 'field list'
（登录、注册、改密全挂 —— 不是只有注册挂，因为 AuthRepo 的查询里带了这一列）
```

### 标准流程

```text
1. 改三处 schema：
     · server/src/main/resources/schema-*.sql         （H2，给单测用，用 add column if not exists）
     · docs/migration-mysql/schema-mysql-full.sql     （MySQL 全量，给空库用）
     · server/src/main/resources/schema-mysql-full.sql（同上，两份必须一致）
2. 写一次性补丁：docs/migration-mysql/patch-mysql-<日期>-<主题>.sql
     · 只加不删；用 --force 跑，重复执行的 Duplicate 报错会被跳过
     · 文件头写清「先跑补丁再重启服务」
3. 部署顺序：**执行补丁 → 重启服务**（反了就是上面那个 Unknown column）
4. 验证：
     · SchemaParityTest 绿（它只比表与列，**索引是否存在它不查**，索引要自己确认）
     · 起服务后跑一遍 scripts/selftest_mysql.mjs
```
