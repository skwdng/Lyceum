# MySQL 迁移备忘（本期不做，2026-11-02 记录）

> **结论：本期社区任务不切数据库，B 仓继续用 H2 内存库。**

## 3. 切库前必须解决的 3 个阻塞项

### 阻塞 1（必修）：`MatchService` 两行 Timestamp 强转

```java
// server/src/main/java/com/siyige/service/MatchService.java:140
Instant deadline = ((java.sql.Timestamp) dl).toInstant();
// server/src/main/java/com/siyige/service/MatchService.java:407
long left = dl == null ? 0 : java.time.Duration.between(Instant.now(), ((java.sql.Timestamp) dl).toInstant()).getSeconds();
```

- H2 驱动：`getObject()` 对时间列返回 `java.sql.Timestamp` → 正常
- MySQL Connector/J 8.0.23+：同一调用返回 `java.time.LocalDateTime` → `ClassCastException`
- 实测现象：对局 tick 每 265ms 抛一次 `tick <id> failed: ClassCastException`，**对局无法推进**
- 修法：两处强转改为兼容分派（`instanceof Timestamp / LocalDateTime / OffsetDateTime`）

### 阻塞 2（必修）：`Store.java:177` 的 H2 专有 `merge into`

```java
jdbc.update("merge into sy_brief(topic_id, side, content) key(topic_id, side) values(?,?,?)", ...);
```

MySQL 无 `MERGE ... KEY`，需改成 `insert ... on duplicate key update`（作战卡功能）。

### 阻塞 3（需评估）：其余时间类型假设未穷尽

全仓共 3 处 `java.sql.Timestamp` 引用（`Store.java` import、`MatchService:140/407`）。
需在 MySQL 下跑完 T10 三个自检脚本才能确认无遗漏。

### 6.2 全量 schema：`schema-mysql-full.sql`

`schema-mysql.sql` 是 2026-11-02 的快照（13 张表，只覆盖辩论主链路）。
**现在以 `schema-mysql-full.sql` 为准** —— 它按当前仓库状态翻译了全部 **42 张表**（351 列 / 52 个索引名），
包含这一期间新增的：

```
sy_tag / sy_post_tag            帖子标签
sy_config / sy_config_log       参数管理
sy_alert / sy_alert_mute        管理台告警
sy_sensitive_word               屏蔽词
sy_module_view / sy_daily_active 埋点统计
```

翻译规则（脚本机械转换 + 人工校对）：

| H2 写法 | MySQL 8 写法 | 原因 |
|---|---|---|
| `bigint generated by default as identity` | `bigint not null auto_increment` | MySQL 无 identity 列 |
| `clob` | `longtext` | 类型名不同 |
| `boolean` | `tinyint(1)` | MySQL 的布尔是别名 |
| `create index if not exists X on T(...)` | 表内 `key X (...)` | MySQL 8 的 CREATE INDEX 没有 IF NOT EXISTS |
| `alter table T add column if not exists c ...` | 折进建表语句 | ADD COLUMN 同样没有 IF NOT EXISTS |

### 6.6 验证 tick 必须用房间对局（kind=room）

在 mysql profile 下验「对局能不能自己推进」时，**不能用默认参数开对局**：

```text
POST /api/matches { mode:'FULL', seats:['A1','B1'], topicId:'t3' }            ← kind 缺省 = solo
  solo 的 stepSeconds() 直接返回 0（不限时）→ deadline_at 为 NULL → tick 本来就不推进
  用这个验会误判成「MySQL 下 tick 挂了」

POST /api/matches { mode:'FULL', seats:['A1','B1'], topicId:'t3', kind:'room' }  ← 正确
  turns 会自己 1 -> 2 -> 3 增长，remainingSec 倒数，日志里不应出现 ClassCastException
```

2026-11-27 实测（mysql profile）：`kind=room` 对局 turns 1→2→3，无异常；
重启后数据仍在（14 用户 / 12 对局 / 127→128 发言），H2 下同样的重启会归零。

## 7. 2026-11-27 并发验证：MySQL 下抓到两个真 bug（已修）

H2 内存库把写操作串行化了，很多竞态在 H2 下几乎撞不上；换 MySQL 后是**必现**。
下面是这批实测出来的两处，都在钱包里。

### 7.1 `sy_wallet` 建行撞主键 -> 并发开局 500

```text
现象：同一用户并发开 5 局，4 个 500
日志：Duplicate entry 'xxx' for key 'sy_wallet.PRIMARY'
原因：WalletRepo.ensure 是「先 count 为 0，再 insert」，两个线程都数到 0 就都去 insert
改法：ensureRow 吞掉 DuplicateKeyException（行已经在了就达到目的）
```

### 7.2 体验金重复赠送（金额翻 10 倍）

```text
现象：全新用户 10 个并发请求 /api/wallet -> 送了 10 次体验金（余额 1000 而不是 100）
原因：WalletService.ensureWallet 是「查历史为空 -> 送礼 -> 记一笔」，
      两个线程都能查到空；而且 MySQL 默认 REPEATABLE READ —— 
      事务快照在第一次普通 select 时就定了，普通 count 看不到别人刚提交的流水
改法：WalletRepo.grantIfNoHistory 上加 @Transactional，先在钱包行 for update 排队，
      再用**锁定读**（select ... limit 1 for update）判断有没有流水，最后才赠送
```

### 7.3 修复后实测（mysql profile）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 全新用户 10 个并发 `/api/wallet` | 10 条 GRANT，余额 1000 | **1 条 GRANT，余额 100** |
| 同一用户并发开 5 局 | 1 成功 + 4 个 500 | 1 成功 + 4 个 409（余额不足，正确的业务拒绝） |
| 并发充值 10 次 × 100 分 | — | 余额 1100 = 体验金 100 + 充值 1000，**一分不差** |

单测：`WalletGrantRaceTest`（8 线程同时首用，断言只有 1 条 GRANT）。
注意它在 H2 上**没修也能过**（H2 写串行），真正的证据是上面的 MySQL 实测。
