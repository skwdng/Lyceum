# 举报与管理员接口契约（治理模块，v1.0 · 2026-11-03）

> **范围**：`/api/admin/**` 八个管理接口 + 用户侧三个治理接口 + 两种处罚的拦截规则。
> **上游决策**：`D:\siyige-v2\举报与管理员-方案.md`（D1–D11 已定，不再讨论）。
> **与其它契约的关系**：
> - 用户侧 3 个接口属于**社区**接口，登记在 `docs/社区接口契约.md`；本文件只做交叉说明。
> - 管理员登录**不是**用户登录，令牌与 `docs/认证接口契约.md` 的那套完全隔离。

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 前缀 | `/api/admin/**`（只挂 `AdminAuthFilter`） |
| 令牌 | `Authorization: Bearer <adminToken>`；`payload` 带 **`typ=ADMIN` + `role=ADMIN`**，`sub` = `sy_admin.id` |
| 存放 | 前端 `localStorage['sy_admin_jwt']`（与用户令牌 `sy_jwt` 完全隔离） |
| 放行 | `/api/admin/auth/login` 不需要令牌，且**不解析**请求里可能带的旧令牌 |
| 有效期 | 2 小时（与用户令牌同一套 `JwtService`） |
| 错误体 | `{"code":"NOT_ADMIN","message":"..."}`；`code` 机读、`message` 可读 |
| 身份参数 | **不接受**任何"操作人 id"参数——`handled_by` / `banned_by` 一律取 `AdminContext.requireId()` |

### 2.1 队列 item（`GET /reports` 的 items 元素）

```json
{
  "targetType": "POST",          // POST | COMMENT
  "targetId": 12,
  "reportCount": 3,              // 该目标的举报条数
  "reporterCount": 3,            // 去重后的举报人数
  "multiReport": true,           // reporterCount >= 3 时为 true（前端打红标）
  "reasons": ["SPAM","ABUSE"],   // 该目标出现过的原因
  "firstReportId": 7,            // 点「处理」用它打开详情
  "firstAt": 1793694799683,      // epoch 毫秒
  "lastAt": 1793694800086,
  "targetExists": true,          // 内容是否还在（软删后 false，但**仍在列表里**）
  "targetSummary": "帖子标题或评论正文前 60 字",
  "targetAuthor": "author01",
  "postId": 12                   // 仅 COMMENT 有：所属帖子
}
```

排序：**举报人数降序 + 首次举报时间升序**（D7）。`status` 缺省 `PENDING`，只接受 `PENDING|ACCEPTED|REJECTED`。

### 2.2 详情（`GET /reports/{id}`）

```json
{
  "report":  { "reportId":7, "targetType":"POST", "targetId":12, "reporterId":"rep01",
               "reporterName":"rep01", "reason":"ABUSE", "detail":"…",
               "status":"PENDING", "action":null, "createdAt":0, "handledAt":null },
  "target":  { "targetType":"POST", "targetId":12, "exists":true, "deleted":false,
               "author":"author01", "authorName":"author01", "createdAt":0,
               "title":"…", "body":"全文…" },     // COMMENT 时为 body + postId
  "reports": [ /* 同目标的全部举报，含各自的 reporterName */ ]
}
```

### 2.3 处理（`POST /reports/{id}/resolve`）

| `action` | 含义 | 结果状态 |
|---|---|---|
| `IGNORE` | 举报不成立 | 全部 PENDING → **REJECTED** |
| `DELETE` | 软删内容 | → ACCEPTED |
| `BAN` | 社区禁言 `banDays` 天（必填 1/3/7） | → ACCEPTED |
| `DELETE_AND_BAN` | 删除 + 禁言（`banDays` 必填） | → ACCEPTED |

- **一次处理该目标下全部 PENDING**，不是只处理传入的那一条。
- 目标已被删除时：删除步骤跳过、拿不到作者则禁言跳过，**举报照样结案**（不返回 500）。
- `note` ≤200 字，进日志与处理记录的 `detail`（形如「删除内容，理由：确认广告」）。
- **每次处理都会写一条处理记录**（`sy_audit_log`，`action=REPORT_RESOLVE`），见 §2.4。

#### 处理会产生社区通知（2026-11-04 新增，V3）

| 动作 | 通知 type | 收件人 | 文案 |
|---|---|---|---|
| 删帖（`DELETE` / `DELETE_AND_BAN` 里的删除） | `POST_DELETED` | **帖子作者** | 「你的帖子《标题》被管理员删除，理由：{note}」 |
| 删评论 | `COMMENT_DELETED` | **评论作者** | 「你的评论「正文」被管理员删除，理由：{note}」 |
| 禁言（`BAN` / `DELETE_AND_BAN`，以及用户管理页手动禁言） | `MUTED` | 被禁言者 | 「你被社区禁言：至 yyyy-MM-dd HH:mm，理由：{note}」 |
| 解禁（`POST /users/{id}/unban`） | `UNMUTED` | 被解禁者 | 「你的社区禁言已被解除」 |
| 全站封禁（`POST /users/{id}/status` 且 `status=0`） | `BANNED` | 被封禁者 | 「你的账号被全站封禁，理由：{note}」 |
| 全站解封（`status=1`） | `UNBANNED` | 被解封者 | 「你的账号已解封」 |

- **作者自己删自己的内容不发**（社区侧软删不触发）；管理员删才发。
- 通知失败**不影响**处理结果（`NotificationService` 内部整段 try/catch + warn）。
- 全站封禁期间用户登不进来，`BANNED` 通知实际是**解封后补看**的历史记录（已确认接受）。
- 通知表结构与未读计数规则见 `docs/社区接口契约.md` §3.2。

## 2.4 处理记录与一键恢复（2026-11-03 新增）

### 记什么（范围收窄，用户决策 2）

| 记 | 不记 |
|---|---|
| 管理员处理举报（IGNORE / DELETE / BAN / DELETE_AND_BAN） | 管理员登录、登录失败 |
| 管理员撤销某次处理（一键恢复） | 管理员改密 |
|  | 用户侧任何动作（注册、登录、举报、改密） |
|  | 用户管理页的**手动禁言/解封**（也就没有恢复按钮） |

> 这张表只回答一个问题：「谁对被举报内容做了什么，能不能反悔」。
> 表极小、语义单一，和「恢复」功能天然配对。

### 表结构（`schema-security.sql`）

```sql
create table sy_audit_log (
  id bigint identity, report_id bigint not null, admin_id bigint not null,
  admin_name varchar(64), action varchar(24) not null,   -- REPORT_RESOLVE | RESTORE
  verdict varchar(24),                                    -- IGNORE|DELETE|BAN|DELETE_AND_BAN
  target_type varchar(8), target_id bigint,
  detail varchar(500),                                    -- 人读，**禁止任何凭据**
  undo_at timestamp, undo_by bigint, ip varchar(64),
  created_at timestamp not null default current_timestamp);
```

### `GET /api/admin/audit` 的 item

```json
{ "id": 6, "reportId": 12, "adminId": 1, "adminName": "admin",
  "action": "REPORT_RESOLVE", "verdict": "DELETE",
  "targetType": "POST", "targetId": 100,
  "detail": "删除内容，理由：确认广告", "ip": "127.0.0.1",
  "createdAt": 1793710764144, "undoAt": null, "undone": false,
  "canRestore": true }
```

`canRestore` = `action=REPORT_RESOLVE` **且** `undo_at` 为空 **且** `verdict ∈ {DELETE, DELETE_AND_BAN}`。
所以 `IGNORE`（本来没动内容）与纯 `BAN`（只禁言）**没有可恢复内容**，前端不给恢复按钮。

### 一键恢复做了什么

| 当初的 verdict | 恢复动作 |
|---|---|
| `IGNORE` | 不可恢复（本来就没动内容）→ 409 `NOT_RESTORABLE` |
| `DELETE` | 目标 `status` 2 → 1，**内容重新可见** |
| `BAN` | 没有可恢复内容 → 409 `NOT_RESTORABLE`（要解禁去用户管理页） |
| `DELETE_AND_BAN` | **只恢复内容**；禁言**不动**（用户决策：恢复不接触禁言） |

一次恢复的三件事：
1. 原记录 `undo_at = now, undo_by = 当前管理员`（原文保留，只标记已撤销）
2. **另插**一条 `action=RESTORE` 的记录（谁撤销、什么时候、撤销了什么）
3. 关联举报 `ACCEPTED → REOPENED`

`REOPENED` 是**终态**：**不回处理队列**（队列默认只查 `PENDING`）、也不能再被处理
——恢复是"反悔一次"，不是"重开一轮审判"。它仍能在「我的举报」与处理记录里看到。

失败口径：能恢复却没恢复成，一律 **409**（不假装成功）——
`ALREADY_RESTORED`（已撤销过）/ `NOT_RESTORABLE`（无内容可恢复，或目标已不存在/已可见）。
失败时**不留半截状态**：不置 `undo_at`、不插 `RESTORE`、不动举报状态。

### 禁言记录上的 `report_id`

`sy_community_ban.report_id` 标明这次禁言由哪条举报触发，**只作归属标记与审计追溯**；
一键恢复**不据此撤销禁言**（用户确认）。要解禁请走 `POST /api/admin/users/{id}/unban`。


### 4.2 `schema-security.sql`（改密 + 审计，2026-11-03 新增）

```sql
alter table sy_user            add column pwd_changed_at timestamp;
alter table sy_admin           add column pwd_changed_at timestamp;
alter table sy_community_ban   add column report_id      bigint;
create table sy_audit_log(...)  + ix_audit_report(report_id,created_at) + ix_audit_time(created_at)
```

- `pwd_changed_at`：改密时间。令牌 `iat` 早于它 → 401 `TOKEN_STALE`。
  **比较时截断到秒**（`iat` 只有秒精度，否则改密后同一秒的新令牌会被误踢）。
- `report_id`：这次禁言由哪条举报触发。**只作标记**，恢复不据此撤销禁言。

### 4.3 `sy_report.status` 的四个取值

| status | 含义 | 在队列里吗 |
|---|---|---|
| `PENDING` | 待处理 | ✅（队列默认只查它） |
| `ACCEPTED` | 已处理（删了/禁言了） | ❌ 但可在处理记录里看到 |
| `REJECTED` | 已驳回（忽略） | ❌ |
| `REOPENED` | 处理被撤销、内容已恢复 | ❌ **终态，不回队列、不能再处理** |

- **不动** `schema.sql` / `schema-community.sql` / `schema-auth.sql` / `schema-admin.sql` 一行。
- 复用 `sy_user.status`（`0` 封禁 / `1` 正常）作为**全站封禁开关**。
- 种子管理员：`admin / admin123`（Argon2id 常量哈希；**仅本地演示，生产必须改**）。

## 5. 错误码

| code | HTTP | 场景 |
|---|---|---|
| `INVALID_PARAM` | 400 | 参数不合法（action / banDays / status / 原因超长 / 请求体不是 JSON）；改密时旧密码不正确、新旧相同也算 400 |
| `BAD_CREDENTIALS` | 401 | 管理员账号或密码错误（账号不存在与密码错文案一致） |
| `UNAUTHORIZED` | 401 | 管理端未带令牌 / 令牌无效 |
| `TOKEN_STALE` | 401 | 管理员改密后，改密之前签发的令牌立刻失效 |
| `NOT_ADMIN` | 401（管理员令牌调社区）/ 403（用户令牌调管理端 / 管理员已停用） | 令牌类型不匹配 |
| `ACCOUNT_DISABLED` | 401 | 全站封禁（登录接口与社区过滤器都会返回） |
| `MUTED` | 403 | 社区禁言中，`message` 带到期时间 |
| `REPORT_NOT_FOUND` | 404 | 举报不存在 |
| `USER_NOT_FOUND` | 404 | 用户不存在 |
| `AUDIT_NOT_FOUND` | 404 | 处理记录不存在 |
| `ALREADY_REPORTED` | 409 | 同一人重复举报同一目标 |
| `ALREADY_RESTORED` | 409 | 这条处理记录已经撤销过了 |
| `NOT_RESTORABLE` | 409 | 没有可恢复的内容（IGNORE / 纯 BAN），或目标已不存在/已可见 |
| `TOO_MANY_ATTEMPTS` | 429 | 管理员登录失败次数超限 |
| `SERVICE_UNAVAILABLE` | 503 | Redis 不可用（登录限流依赖） |

## 6. 权限矩阵与两种处罚

| 场景 | 行为 |
|---|---|
| 无令牌访问 `/api/admin/**` | 401 `UNAUTHORIZED` |
| 用户令牌访问 `/api/admin/**` | 403 `NOT_ADMIN` |
| 管理员令牌访问 `/api/community/**` | **401 `NOT_ADMIN`**（不是当匿名放行，避免管理员以普通用户身份发帖/点赞） |
| 社区禁言中：发帖 / 评论 / **编辑帖子** / 点赞 | 403 `MUTED`（`message` 形如「你已被禁言至 2026-11-10 16:34」） |
| 社区禁言中：删除自己的帖或评论、取消点赞、浏览 | ✅ 正常（删除是净化行为，不能卡住） |
| 全站封禁：登录 | 401 `ACCOUNT_DISABLED` |
| 全站封禁：已登录用户的旧令牌 | **下一次请求即 401 `ACCOUNT_DISABLED`**（`JwtAuthFilter` 每次查 `sy_user.status`，**不加缓存**） |
| 禁言 × 全站封禁 | **互不干扰**：解禁不会解封，解封不会解禁 |
| 管理员改密 | 该管理员**所有旧令牌立刻失效**（401 `TOKEN_STALE`），包括当前这一个 |
| `PATCH /api/admin/auth/password` | **不在过滤器放行名单里**（只有 `/api/admin/auth/login` 放行），所以天然要求令牌；身份取 `AdminContext`，不接受请求体自报 id |
| 处理记录 | **只读 + 只能撤销**：没有删除/修改接口，`DELETE /api/admin/audit/{id}` 不开放 |

## 7. 安全要求（改代码前先读）

| 项 | 做法 |
|---|---|
| 管理员密码 | Argon2id，复用同一个 `PasswordEncoder`（参数与用户一致）；改密与用户端共用 `PasswordPolicy` |
| 防账号枚举 | 账号不存在 / 停用时也跑一次假哈希校验，文案统一 |
| 登录限流 | 复用 `LoginRateLimiter`，但用**管理端专属**前缀 `adm:`，与用户端 `auth:` 隔离 |
| 管理端 XSS | `admin.js` 里所有服务端字符串一律 `esc()` 后才拼 `innerHTML` |
| 日志 | 只打 account / userId / targetId，**不打印密码、不打印令牌** |
| 目标已不存在 | 处理时不报 500，按「目标已不存在」把举报结案 |
| **处理记录不含凭据** | `detail` 只写人读业务描述；DTO 的 `toString()` 固定 `<redacted>`；有单测断言审计里不出现 `$argon2` / `eyJ` / `Bearer` |
| **审计写失败不影响主流程** | 所有写入必须经 `AuditLog` 门面，内部 `try/catch + warn`；红线有单测守着 |

## 8. 已知边界

- **全站封禁管不到辩论侧**：`/api/matches`、`/api/records` 等仍用 `?userId=` 自报、无鉴权，
  所以"封了连辩论都用不了"本期只做到「登录进不去 + 社区全接口 401」。
  要真封死得先给辩论侧接鉴权（不在本期范围，方案 R7 已记录）。
- **处理记录只覆盖举报处理与撤销**：管理员登录、改密、用户管理页的手动禁言/解封都不记（决策 2）。
  需要更全的审计得另开表，不要往这张表里塞。
- **恢复不解禁言**：撤销删除只让内容重新可见；禁言到期或到用户管理页手动解禁（决策 E）。
- **`REOPENED` 不能再处理**：恢复是终态反悔，不是重开审判；要重新处置只能重新举报。
- `stats` 只有三个字段，**没有**「今日删除数」——库里没有 `updated_at`，数不出来（决策 D11）。

## 9. 埋点上报（2026-11-11 · 管理台重构 P1 新增）

> ⚠️ 这个接口**不在 `/api/admin/**` 下**，也**不需要管理员令牌** —— 它由普通访客的浏览器调用，
> 数据只是给管理台报表（P3）读。所以 §2 的「管理接口（12 个）」表**不含**它。

| 项 | 约定 |
|---|---|
| 路径 | `POST /api/track/pv` |
| 鉴权 | **匿名可用**：不注册 `JwtAuthFilter`（沿用「不注册即匿名」的既有做法）。带用户令牌时只用来记 UV，**不查黑名单** |
| 请求 | `{"module":"community"}` |
| 成功 | 200 `{"ok":true}` |
| 降级 | 200 `{"ok":false}` —— Redis 不可用时丢弃本次统计；统计不是关键路径，绝不因此让页面报错 |
| 失败 | 400 `{"code":"MODULE_NOT_ALLOWED","message":"..."}` |

`module` 白名单（11 个，只收这些值）：

```text
community  chat  match  solo  video  hot  diag  records  wallet  friends  admin
```

口径（与设计文档《管理台重构-设计方案》§1 / §2 一致）：

- **按模块统计，不按页面路径**；`/login`、`/me`、`/notify` 属于"功能"不是"模块"，不上报
- 同一模块连续切换**不重复上报**（前端 `web/src/utils/track.js` 的 lastModule 去抖）
- 匿名只算 PV；带登录态才进 UV（`AdminLayout` 与主站共用同一份 `sy_jwt`）
- 存储：Redis `pv:cnt:{yyyyMMdd}`（Hash，HINCRBY）+ `pv:uv:{yyyyMMdd}:{module}`（HyperLogLog，PFADD）；
  每 5 分钟把 PV 落进 `sy_module_view`，每小时做一次 UV 快照（取大覆盖，不能累加）
- **活跃用户（DAU）不经过这个接口**：由后端 `@Active` 切面直接打点 `act:dau:{yyyyMMdd}`，
  每天 00:05 落进 `sy_daily_active`（浏览不算活跃）

### 10.2 口径（这些坑踩过一次就别再踩）

| 项 | 约定 | 为什么 |
|---|---|---|
| 区间 | **含今天**的最近 N 天；`days` 全部补零 | 折线不会断成碎片 |
| 时间桶 | 一律 Asia/Shanghai 自然日 | 与埋点、`sy_daily_active` 同一口径 |
| 对局时间 | `sy_match.started_at` | **这张表没有 `created_at`** |
| 收入 | 只算 `kind='RECHARGE'` 的 `amount_cents` | HOLD/SETTLE 是内部扣费流转，不是收入 |
| 发帖 | `status=1`（排除软删除） | 与社区列表一致 |
| 新增用户 | `is_bot=0` | AI 账号（deepseek）不算人 |
| 模块 `uv` | 各日 UV 之和（**人天**），另给 `uvPeak` 单日峰值 | 区间去重需要每天的 HLL 还在，而 Redis 只留 3 天 |
| WAU / MAU | Redis `PFMERGE` 合并最近 7 / 30 天 `act:dau:*` 后 `PFCOUNT` | 把每天 DAU 相加会把同一个人算成好几个人 |
| 席位分布 | `sy_seat` 当前占位（正方/反方） | 该表只保存当前房间状态，没有历史 |
| 存量为 0 时 | `deltaPct` 返回 `null` | 「从 0 变成 5」没有百分比意义，前端显示「新增」 |

### 10.3 错误码

`400 INVALID_RANGE`（range 不是 `Nd` / 日期格式错 / 超过 366 天 / from>to）、
`400 INVALID_METRIC`、`400 INVALID_DIM`、`400 INVALID_GRANULARITY`（目前只支持 `day`，小时级未采集）。
