## 一句话

**Lyceum（思弈阁）是一个 AI 4v4 辩论训练系统**：8 个 AI 辩手各占一个席位、各有自己的辩论风格与推理策略，用户在其中一个席位上和整支队伍对辩，系统按真实赛制推进 12 个环节，结束后给出五维评分与逐回合点评。

在线试用：<http://120.24.204.138:8787/siyige/>

## 现在能做什么（已完成）

### 对辩主流程
- [x] 标准 12 步赛制：立论 → 驳立论 → 质询 → 自由辩 → 总结
- [x] 8 个 AI 席位，每个席位独立人设（风格 / 温度 / 思考时长 / 推理策略）
- [x] 席位自选：任意挑一个位置，其余 7 席由 AI 补位

- [x] 自由辩抢拍：8 秒窗口，抢到才拿到话筒
- [x] 抓漏玩法：AI 每轮埋一个逻辑漏洞，玩家从 5 类里指认，正确 +3
- [x] 每步限时 + 打字自动续时（单人模式不限时）

### 好友 + 私聊 + 邀请组队（已完成，2026-11-07）
- [x] 好友：搜索（id/账号精确优先、昵称前缀兜底，最多 10 条）→ 发请求（带附言 ≤100 字，超出静默截断）
  → 接受 / 拒绝 → 列表 → 删除。关系用**字典序单行**存，删一边就是双向解除
- [x] 双向互发直接成为好友（不然两边都卡在「已发送」谁也没法接受）；被拒后可重发；拒绝不通知
- [x] AI 账号三重拦截：搜不到、加不了（400）、聊不了
- [x] 私聊：只有好友能发（否则 403），消息过敏感词打码（原文不落库），单条 ≤2000 字
- [x] 历史用**游标**翻页（`beforeId`），断线补拉用 `afterId`——一条不丢；不用 offset（会被新消息挤错位）
- [x] **未读在 Redis**：`social:unread:{userId}` Hash，一次 `HGETALL` 同时喂饱侧栏角标与会话列表每行；
  数据库只存「读到哪条」，标已读时先用一条 SQL 算出实际读掉几条再 Lua 原子递减
  （换成 MySQL 后轮询也不会产生查询压力）
- [x] 实时：原生 WebSocket（`/ws/chat`，令牌走 `?token=`）+ 25 秒心跳 + 指数退避重连 + 重连按 `afterId` 补拉
- [x] 兜底：WS 连续失败 3 次自动降级 3 秒轮询，**收发都还能用**（发送走 `POST /api/social/messages`），
  WS 恢复后自动切回实时
- [x] 多端：同一账号手机+电脑同时在线，两端都收到推送
- [x] 侧栏新增「消息」入口 + **独立角标**（与「通知」各算各的，进通知页不会清掉消息红点）
- [x] 邀请组队：房主在房间页点「邀请好友」→ 对方在聊天窗看到卡片（房间号高亮 + 加入按钮）→
  一键进房（与手动输房间号同一条路径）。INVITE 是消息的一种 type，不新建表
- [x] 自检：552 个单测（本期新增 99 个）+ 浏览器自检 **32 项**（好友 9 / 聊天 8 / WS 10 / 邀请 5）
- [x] 实测：对方发消息 **171ms** 出现在界面；断线重连后历史自动补齐；降级轮询延迟 ≤3 秒
- [x] 修复（2026-11-07 用户实测反馈）：聊天记录一多，输入框会被顶到页面最下面，要手动滑到底才看得见。
  根因两处：① `.chat` 容器是 grid，隐式 `auto` 行跟着内容长高 → 显式 `grid-template-rows:minmax(0,1fr)`；
  ② flex 子项默认 `min-height:auto`，`overflow:auto` 不生效 → `.chat-main` / `.chat-msgs` 补 `min-height:0`。
  顺带修掉两个连带问题：打开会话不自动贴底（滚动放在 render 之前做的，DOM 一换就归零）、
  翻历史时来新消息会被拽回（渲染后补发的 scroll 事件被误判成"用户滚到顶"，误触发了加载更多）
- [x] 布局回归已固化进自检 L1~L6（宽屏/手机、打开贴底、发送后贴底、连发不顶动、翻历史不被抢、单栏）
- [x] 修复（2026-11-07 用户实测反馈）：有未读时点「消息」，界面显示了和第一个人的聊天记录，但未读没清掉。
  两个根因：① 判断「是否正在看这个会话」只比了 `convId` 没比 `view` —— 离开消息页后 `convId` 仍保留，
  别处来的消息被自动标已读，红点永远不亮（更严重，会漏消息）；
  ② 回到消息页只刷新会话列表，不重拉当前会话也不标已读 → 看着像看过了，其实没读。
  已改为：只有「停在消息页 **且** 打开的就是这个会话」才算已读；进消息页一律重新拉取当前会话并标已读
- [x] 未读语义回归固化进自检 U1~U4（在别页收消息红点要亮且不误标 / 回来自动打开并清零 /
  刷新后列表态不误标、点开才清 / 看 A 会话时 B 会话的消息仍算未读）
- [x] 修复（2026-11-07 用户实测反馈）：**换账号串状态**。退出后用同一个标签页登录另一个账号，
  点「消息」会出现「标题是自己、看的是上一个账号的会话、未读消不掉、发消息报失败」。
  根因：登录/注册/退出都没有清 `S.chat` / `S.social` / WebSocket 补拉位置，旧账号的 convId 与 peer 被沿用。
  已加 `socialReset()`（登录/注册/退出都调），并让 `chatOpen` 先丢弃旧 peer 与旧消息、
  加载失败就地显示可重试错误（不再拿旧数据分析），`loadChat` 发现当前会话不在列表里就作废。
  顺带修掉「点没有未读的会话看不到历史、发一条才出现」——同一个根因（convId 指向了旧账号的会话）

## 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Java 17 · Spring Boot 3.3 · JdbcTemplate · SSE |
| 数据库 | H2（内存/文件），Redis（热榜 + 社区） |
| 前端 | 原生 JS，按模块拆分（无框架、无构建步骤） |
| 大模型 | DeepSeek（OpenAI 兼容接口） |
| 部署 | 阿里云 2C1G · systemd · Nginx 反代 |

### 代码结构

```
server/src/main/java/com/siyige/
├── api/          接口层
├── service/      赛制引擎、评分、复盘
├── ai/           AI 辩手（人设、提示词、生成）
├── community/    社区模块（独立包，合作方负责）
├── auth/         登录与鉴权（注册 / JWT / 过滤器 / 限流 / 改密 / 对局归属 MatchAccess）
├── admin/        管理后台（独立账号体系 / 举报处置 / 处理记录与恢复）
├── repo/         数据访问
└── engine/       赛制定义

server/src/main/resources/static/
├── index.html    空壳
├── admin.html    管理后台（独立页，不加载 core.js）
├── css/app.css   样式
└── js/
    ├── core.js   全局状态、请求、路由
    ├── admin.js  管理后台逻辑（独立，不依赖 core.js）
    └── views/    一人一块：solo / match / review / hot / diag / records / room / community / auth
```
