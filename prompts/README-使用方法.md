# 思弈阁 AI Coding 提示词包 · 使用说明

## 这个包是什么

7 个文件，覆盖从"空目录"到"可验收系统"的全过程。每个阶段文件里的**代码块就是你要粘给 AI 的话**，代码块外面的正文是你自己的验收标准，不要粘给 AI（粘了它容易自作主张）。

```
prompts/
├── 00-总纲-AGENTS.md              ← 放进项目根目录，改名 AGENTS.md / CLAUDE.md
├── 01-阶段1-骨架与配置.md
├── 02-阶段2-认证与辩题.md
├── 03-阶段3-对辩SSE主链路.md      ← 核心，最重要
├── 04-阶段4-评分复盘与画像.md
├── 05-阶段5-前端原型转Vue.md
├── 06-阶段6-压测部署与结题.md
└── README-使用方法.md             ← 本文件
```

## 三步启动

### 第 1 步：把总纲放进项目

```bash
# 按你用的工具选一个名字，内容都是 00-总纲 那份
cp prompts/00-总纲-AGENTS.md ./AGENTS.md        # Codex / 通义灵码 / 通用
cp prompts/00-总纲-AGENTS.md ./CLAUDE.md        # Claude Code
mkdir -p .cursor/rules && cp prompts/00-总纲-AGENTS.md .cursor/rules/project.md   # Cursor
```

### 第 2 步：每次开新会话，先发这一句

```
先完整读一遍项目根目录的 AGENTS.md，然后只回答一句话：你读到了哪几条硬性约束。
先不要写代码。
```

**为什么必须有这一步**：AI 编码工具最大的浪费是"没读规则就开写"。让它复述规则，你就知道它真读了没有。它复述完，你再发阶段任务。

### 第 3 步：按阶段推进，一次一个提示词

```
阶段1 → 验收 → 阶段2 → 验收 → 阶段3A → 3B → 3C → 阶段4A/4B/4C → 阶段5A/B/C/D → 阶段6A/B/C
```

**铁律：每个提示词跑完、验收通过，再发下一个。** 一次发两个阶段的提示词，是返工率最高的用法。

## 万能尾注（贴在每个提示词末尾，强制 AI 做自检）

```
【收尾硬性要求】
1. 先输出改动清单：每个文件一行，标明「新建 / 修改」和一句话说明
2. 输出验证步骤：我需要按顺序执行哪些命令，预期看到什么
3. 明确列出你做的假设（尤其是你不确定我意图的地方）
4. 如果任何一处你没把握，标注 "TODO: 待确认" 并说明，不要自己编一个实现
5. 不要声称"已完成"——只说你做了什么、怎么验证
```

## 跑偏时的纠正话术（比重新描述需求有效得多）

AI 编码跑偏有固定模式，用固定句式纠，一句话就能拉回来：

| 症状 | 纠正话术 |
|---|---|
| 偷偷换了技术选型 | 「技术栈锁在 AGENTS.md 第 1 节，不要替换。把 [X] 改回 [Y]，只改这一处，不要顺带重构其他文件。」 |
| 一次性重写了 5 个文件 | 「回退这次改动。只保留 [目标文件] 的修改，其余恢复。下次改动超过 3 个文件前先停下来问我。」 |
| 编造了不存在的 API | 「这个方法我不确定存在。请按官方文档能查到的最保守写法重写，如果确实不确定，用 TODO 标注并给出两种可能的实现方案让我选。」 |
| 声称完成但没编译 | 「在回答之前先执行 mvn -q compile，把真实输出贴给我。没跑就别说完成。」 |
| 用 SseEmitter 写流式 | 「本项目的流式必须用 Flux，理由见 AGENTS.md 第 5 节禁止事项。请改为返回 Flux<ServerSentEvent<String>>。」 |
| 用 `.call()` 不是 `.stream()` | 「症状是等 3 秒一次性出全文，说明没走流式。检查 service 里是否用了 .stream().content()。」 |
| 加了没批准的依赖 | 「这个依赖不在 AGENTS.md 的允许清单里。请用已有依赖实现，或者说明为什么非它不可。」 |
| 把 mock 数据留下了 | 「清理生产代码里的 mock/测试数据，包括写死的假 token、假 userId、System.out。列出你清掉的每一处。」 |
| 代码能跑但结构乱 | 「这次改动违反了 AGENTS.md 第 2 节的目录规范（[具体违反点]）。请移动文件到正确位置，不要改逻辑。」 |

## 卡住时的三个救命提示词

### 提示词 1：让它自己诊断

```
现在这个功能没达到预期。现象是：【贴报错 / 贴实际现象 / 贴预期】。
请按以下顺序分析，不要直接改代码：
1. 列出 3 个最可能的原因，按可能性排序
2. 对每个原因，给出一个"用 10 秒能验证"的检查命令或日志点
3. 等我确认是哪个原因后，你再改
```

### 提示词 2：让它解释而不是重写

```
不要改代码。用 5 句话解释这段代码的执行流程：
【贴代码】
特别注意：Flux 在什么时候真正订阅、异常会在哪个线程上抛、ThreadLocal 在哪个环节被清理。
```

### 提示词 3：让它生成可复现的最小验证

```
为这个功能写一个最小的可复现验证：
- 一个 curl 或 .http 文件
- 一个单元测试（只测这一个方法，不要写其他测试）
- 预期输出的确切内容
我要用它在 1 分钟内判断"到底通没通"。
```

## 我按你的编程习惯做的几处定制

| 定制点 | 依据 |
|---|---|
| 大量复用 Caffeine + Redis 两级缓存、`@RateLimit` 思路 | 你 `123c` 里已经实现过，AI 照这个风格写你 review 最快 |
| SSE 明确要求用 `Flux` 而非 `SseEmitter` | 你 `123c` 用的是 SseEmitter，但 AI 场景下 Flux 才有背压，这个差异必须在提示词里讲死，否则 AI 会照你旧仓库的风格写 |
| Docker Compose 编排 | 你 `123c` 的 `docker-compose.yml` 已经很规范，直接沿用结构 |
| 强调"多环境 profile + .env 隔离密钥" | 你 `LifeKit` 仓库的 README 里对密钥管理的意识很好，保持一致 |
| 强调"改完必须自检并输出改动清单" | 你 LifeKit 有 1994 条断言的工程化习惯，这里把它迁移成"AI 交付自检" |
| 前端要求"照抄原型，不要重新设计" | `siyige-prototype.html` 已经是成品级完成度，重新设计只会更差 |

## 一个提醒

这套提示词里，**阶段 3 是整个项目的生死线**。其他阶段做砸了还能补，阶段 3 卡住就是"系统跑不通"。

阶段 3 如果超过 5 天还没跑通"逐字输出"，把这三个信息发我：① `curl -N` 的原始输出 ② 后端的 `DebateAiService` 全文 ③ 依赖树的 `mvn dependency:tree` 输出片段。这三个能定位 95% 的流式问题。
