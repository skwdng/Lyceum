# 阶段 3｜对辩 SSE 主链路（核心，预计 4–5 天）

> 这是整个项目最关键的一段。做完这一阶段，项目就"活"了 —— 能真的和 AI 辩论并看到逐字输出。
> 建议拆成 A（后端流式）→ B（上下文与落库）→ C（模型闸门）三次任务，每次做完先跑通再继续。

## 提示词 A：辩手流式对话（先不落库、不做评分）

```
读 AGENTS.md。本次只做一件事：让 AI 辩手能以流式方式回答，并通过 SSE 逐字推给前端。

【任务】
1. 在 ai/prompt/ 下新建 debate-system.txt，写入辩手系统提示词（内容见下方【提示词内容】）
2. ai/DebateAiService：
   - 注入 debateChatClient
   - 方法：Flux<String> speak(String sessionId, String topic, String side, String userSpeech)
   - 组装：system(辩手提示词 + 辩题 + 立场) + user(用户发言)
   - 用 .stream().content() 返回 Flux<String>
3. controller/DebateController：
   @PostMapping(value="/api/debate/{sessionId}/speak", produces=MediaType.TEXT_EVENT_STREAM_VALUE)
   返回 Flux<ServerSentEvent<String>>
   - event 名用 "delta"，data 为文本片段
   - 结束时追加一个 event=done、data=[DONE] 的事件
   - 出错时推 event=error，data 为中文错误提示，不要让异常直接抛成 500
4. 前端联调用例：在 docs/debate.http 里写一段可直接运行的 curl

【提示词内容（写入 debate-system.txt）】
你是「思弈阁」的 AI 辩手，正在与一位学习者进行{level}难度的辩论训练。
本场辩题：{topic}
你的立场：{side}（正方=支持，反方=反对）

发言规则：
1. 每次发言不超过 300 字，先亮明观点，再给 2-3 条可核查的论据；
2. 必须正面回应对方上一轮提出的最后一个论点，不允许回避或自说自话；
3. 不确定的数据不要编造，可以说"这一点需要数据支撑"；
4. 语气坚定但保持辩论礼仪，不使用人身攻击；
5. 不要输出"作为AI"之类的自我指涉，你就是场上的辩手。

【技术硬约束】
- 必须用 Reactor 的 Flux，禁止 SseEmitter
- 必须设超时：.timeout(Duration.ofSeconds(60))，超时推 event=error
- 不能用 @CrossOrigin("*")，CORS 在 WebConfig 里统一配置，只放行 http://localhost:5173
- 不要在 controller 里写业务，组装逻辑放 service
- Flux 是惰性的：方法返回 Flux 时并不会立刻调用模型，确保日志埋点放在 doOnSubscribe 里而不是方法体第一行

【完成后输出】改动清单 + 一个能直接看到逐字输出的 curl + 如果前端用 fetch 流式接收，给出解析 SSE 的 JS 片段
```

### 验证方式（必须看到"逐字"而不是"一次性蹦出"）

```bash
curl -N -X POST "localhost:8080/api/debate/sess-001/speak" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"topic":"人工智能生成内容是否应当享有著作权","side":"pro","level":"进阶","speech":"我方认为AI生成内容应当享有著作权，因为创作意图来自人类。"}'
```

`-N` 是关键（禁用缓冲）。**如果文字是一次性全出来的，说明有缓冲**，按这个顺序排查：

| 排查点 | 检查方式 |
|---|---|
| Nginx 缓冲 | `proxy_buffering off;` 是否生效 |
| Spring 压缩 | `server.compression.enabled=false` |
| curl 缓冲 | 是否漏了 `-N` |
| 代码用了 SseEmitter | AI 有没有偷偷换成 SseEmitter（常见跑偏） |
| 模型本身不流式 | 检查是否误用了 `.call().content()` 而不是 `.stream().content()` |

## 提示词 B：会话上下文 + 消息落库

```
继续阶段 3。本次做上下文管理与持久化。

【任务】
1. 新增两张表（写进 init.sql 并给增量 SQL）：
   t_debate_session：id, user_id, topic_id, topic_title, side, level, status(RUNNING/FINISHED), round_count, created_at, finished_at, deleted
   t_debate_message：id, session_id, role(USER/AI), round_no, content(text), token_count, ttft_ms, created_at

2. ChatMemory 配置：
   - 用 MessageWindowChatMemory，maxMessages=12（约 6 轮问答）
   - 底层 ChatMemoryRepository 用 Redis 实现（spring-ai-starter-model-chat-memory-repository-redis 已引入）
   - 引入 MessageChatMemoryAdvisor，conversationId 用 sessionId
   - 【重点】ChatMemory.CONVERSATION_ID 必须每次调用都传，不传会抛 IllegalArgumentException

3. 落库时机：
   - 用户发言：进入接口后立刻落库（role=USER, round_no=当前轮次）
   - AI 回复：流式结束后落库完整文本（不要在流式过程中逐 chunk 写库）
   - 记录 ttft_ms（首个 token 到达时间）和 token_count

4. 接口补充：
   GET /api/debate/{sessionId}          → 会话详情 + 全部消息（按 round_no 升序）
   POST /api/debate/start               → 创建会话，body: { topicId, side, level }，返回 { sessionId }
   POST /api/debate/{sessionId}/finish  → 结束会话，status=FINISHED

5. 上下文裁剪（性能要求）：
   - 最近 3 轮用原文，更早的轮次如果累计 token 超过 3000，用一次性生成的摘要替代
   - 摘要缓存在 Redis：key=debate:summary:{sessionId}:{uptoRound}，TTL 24h
   - 摘要生成用 judgeChatClient（评委模型做归纳更中立），异步执行，不阻塞对话

【硬性要求】
- 用 Reactor 的 doOnNext / doOnComplete 收集完整文本，禁止用 StringBuilder 在 lambda 外累积（会丢数据）
- 落库失败不能导致流式中断：落库放在 doFinally 里 try-catch 包裹
- 增量 SQL 放 docs/sql/ 目录，文件名带日期

【完成后输出】改动清单 + 表结构 + 上下文裁剪后的实际 prompt 长度对比（估算即可）
```

## 提示词 C：模型配额闸门（防止配额打爆）

```
继续阶段 3。本次做模型调用的并发控制与限流。

【任务】
1. 新增 common/AiGate.java：
   - Semaphore 控制同时在飞的模型调用数，许可数从配置读：siyige.ai.max-concurrent=30
   - 方法：<T> T acquire(Duration timeout, Supplier<T> call)
   - 拿不到许可时抛 BizException(42901, "当前对辩人数较多，已为你排队，请稍后重试")
   - 用 try-finally 保证 release

2. token 预算限流：
   - 注解 @TokenBudget(perMinute = 8000)，AOP 拦截
   - Redis Lua 原子脚本：先 GET 已用，判断 已用+预估 > 预算 则拒绝，否则 INCRBY + EXPIRE 60
   - 预估 token = 输入字符数 / 1.6 向上取整（中文粗略估算即可，注释说明这是估算）
   - 超限返回 BizException(42902, "本分钟 AI 对话额度已用完，请稍候再试")

3. 熔断降级：
   - 用 Resilience4j 的 CircuitBreaker（只引 resilience4j-spring-boot3 一个依赖）
   - 失败率超 50%（10 次窗口）自动打开 30 秒，打开期间直接返回降级提示，不再调模型
   - 降级时前端应看到明确文案，不是空白

4. 指标埋点（Micrometer）：
   - timer: debate.ttft（首 token 延迟）
   - counter: debate.tokens.total（累计 token）
   - gauge: debate.sse.active（活跃 SSE 连接数）
   - counter: debate.model.errors（模型错误数，带 exception 标签）
   - 在 /actuator/metrics 里能看到这几项

【为什么这么做（写进代码注释）】
服务器扛 5000 连接没压力，但模型侧 TPM 配额可能只够 30 并发。
真正的瓶颈在配额，不在 Tomcat。所以限流必须卡在"即将调模型"这一步，而不是卡在 HTTP 入口。

【完成后输出】改动清单 + 如何人为触发限流来验证（给出配置调小的方法）
```

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 逐字输出 | `curl -N` 能看到文字分批出现，肉眼可辨 |
| 2 | TTFT | 日志中 `ttft` 字段 < 1500ms |
| 3 | 多轮上下文 | 第 2 轮提问"我刚才说了什么"，AI 能答对 |
| 4 | 内存窗口 | 第 7 轮后，prompt 里的历史消息数不超过 12 |
| 5 | 落库 | `t_debate_message` 里 USER/AI 记录成对出现，round_no 连续 |
| 6 | 限流 | 把 `max-concurrent` 改成 1，并发两个请求，第二个返回 42901 |
| 7 | 断线 | 流式中间按 Ctrl+C，服务端日志出现取消记录，线程未泄漏 |
| 8 | 指标 | `/actuator/metrics/debate.ttft` 有数据 |

## 这一阶段的三个高危跑偏点

1. **AI 换成 `SseEmitter`**：因为网上 90% 的中文教程讲 SSE 都用 SseEmitter。发现后一句纠正：「必须用 Flux，理由是本项目要背压和虚拟线程友好，SseEmitter 每次 send 会占容器线程」。
2. **AI 用 `.call()` 而不是 `.stream()`**：症状是"等 3 秒一次性出全文"。检查 service 里有没有 `stream().content()`。
3. **`ChatMemory.CONVERSATION_ID` 漏传**：启动不报错，运行时报 `IllegalArgumentException: conversationId must not be null`。这是 Spring AI 1.x 的高频坑。
