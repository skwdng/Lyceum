## 提示词 A：五维结构化评分（评委模型）

```
读 AGENTS.md。本次做评委打分模块。注意：评委与辩手必须是两个独立的 ChatClient，不共享 ChatMemory。

【任务】
1. ai/model/RoundScore.java —— 用 record 定义，字段严格如下（顺序不要改）：
   int logic, int evidence, int rebuttal, int expression, int decorum,
   List<String> flaws, String rebuttalHint, String summary

2. ai/prompt/judge-system.txt：
你是辩论赛的专业评委。你的任务是针对选手的一轮发言给出客观评分。
评判维度与权重：
- 逻辑（logic, 30%）：论点是否成立、推理是否有效、有无偷换概念
- 论证（evidence, 30%）：论据是否充分、是否可核查、有无举证缺失
- 应变（rebuttal, 20%）：是否正面回应对方论点、反驳是否有效
- 表达（expression, 10%）：结构清晰度、语言准确性
- 礼仪（decorum, 10%）：是否保持辩论礼仪

输出要求：
- 五维分数均为 0-100 的整数
- flaws 最多 3 条，每条不超过 12 字，用辩论术语（如"未证明前提""以偏概全""滑坡谬误""诉诸权威""稻草人"）
- rebuttalHint 给一句话的反打建议，不超过 40 字
- summary 一句话点评，不超过 50 字
- 只输出 JSON，不要任何额外解释、不要 markdown 代码块标记

3. ai/JudgeAiService：
   RoundScore score(String topic, String side, String aiSpeech, String userSpeech)
   用 judgeChatClient.prompt()...call().entity(RoundScore.class) 拿结构化结果

4. 健壮性（重点，不要跳过）：
   - 捕获结构化转换异常，重试 1 次（第二次在 prompt 里追加一句"上次输出格式不合法，请严格只输出 JSON"）
   - 两次都失败则返回一个兜底 RoundScore（五维都给 60，flaws=[]，summary="本轮评分暂时不可用"），并记 WARN 日志
   - 校验分数范围：任何维度 <0 或 >100 一律裁剪到边界，不要抛异常中断对话

5. 并行执行（性能要求，必须实现）：
   一轮对辩里，"辩手生成"和"评委打分"必须并行，不允许串行。
   实现方式：controller 里用 CompletableFuture 同时启动两个任务，
   辩手结果走 SSE 流式返回，评委结果在流结束后作为最后一个事件推送（event=score，data 为 JSON）。
   给出完整代码，包含异常处理与超时（评分超时 20 秒，超时后推送 event=score 且 data 为 null，前端显示"本轮评分生成中"）。

6. 落库：t_round_score 表
   id, session_id, round_no, logic, evidence, rebuttal, expression, decorum,
   flaws(json), rebuttal_hint, summary, created_at

【禁止】
- 禁止让评委模型看到 ChatMemory（会带入立场）
- 禁止用字符串拼接 JSON 再手动解析（必须用 entity()）
- 禁止把打分结果和辩手回复放在同一个模型调用里返回（会让辩论质量下降）

【完成后输出】改动清单 + 用一个固定的样例发言展示真实评分结果的 JSON
```

### 关键验证：评分稳定性

```
20 次同一段发言，五维分数的标准差应小于 5。
如果波动过大，把 judgeChatClient 的 temperature 设为 0.1（辩手保持 0.7-0.9）。
```

## 提示词 B：复盘报告（异步生成）

```
继续阶段 4。本次做整场复盘报告，异步生成，不阻塞用户。

【任务】
1. 表 t_report：id, session_id, user_id, status(PENDING/RUNNING/DONE/FAILED), content(text), created_at, updated_at
2. 接口：
   POST /api/report/{sessionId}/generate  → 立即返回 { reportId, status:"PENDING" }
   GET  /api/report/{reportId}            → 返回 { status, content }
3. 生成逻辑（@Async("reportExecutor")，线程池已在阶段1建好）：
   - 汇总整场对话（所有轮次）+ 各轮评分
   - 用 judgeChatClient 生成复盘报告，输出结构为 record ReportContent:
     String overallComment,        // 整场总评 150 字
     List<String> strengths,       // 3 条优势，每条 20 字内
     List<String> weaknesses,      // 3 条不足，每条 20 字内
     List<Drill> drills,           // 2 条专项训练建议 { dimension, reason, suggestAction }
     int finalScore                // 整场综合分 0-100
   - 完成后 status=DONE，content 存 JSON 字符串
4. 状态机：PENDING → RUNNING → DONE / FAILED，失败要记录 error 信息（可加 error_msg 字段）
5. 幂等：同一 sessionId 若已存在 DONE 的报告，直接返回旧的，不重复生成（省 token）

【异步线程池注意】
- @Async 方法必须在另一个 Bean 里调用才生效（同类内调用不走代理），如果你写在同一个 Service 里，请拆成两个 Bean
- 线程池队列满时用 CallerRunsPolicy 还是 AbortPolicy？用 AbortPolicy + 捕获异常返回"当前报告生成繁忙"，不要静默丢任务

【完成后输出】改动清单 + 一次完整调用的时序（先 POST 拿到 PENDING，再轮询 GET 到 DONE）
```

## 验收清单

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 结构化成功率 | 连续跑 10 轮，`entity()` 解析失败次数 ≤ 1 |
| 2 | 评分稳定 | 同一段发言重复评分，标准差 < 5 |
| 3 | 并行生效 | 日志时间戳显示打分与生成本轮耗时重叠（不是相加） |
| 4 | 报告异步 | POST 立即返回（<100ms），30 秒内 GET 到 DONE |
| 5 | 报告幂等 | 重复 POST 同一 session，不新增记录 |
| 6 | 画像 | radar 五维值与数据库均值一致（手工核对一次） |
| 7 | 兜底 | 故意把 API Key 改成错的，评分返回 60 分兜底值，不抛 500 |

## 这一阶段的跑偏点

1. **AI 让评委也带记忆** → 评委被打成"辩手队友"，评分虚高。发现方式是：评分里出现"我方"字样。
2. **AI 用正则解析 JSON** → 模型偶尔输出 markdown 代码块就崩。必须用`.entity()`。
3. **AI 把两个调用串行写** → 用户要等 6 秒而不是 3 秒。检查是否有 `CompletableFuture` 或 `.join()` 前的阻塞。
4. **`@Async` 在自己类里调用自己** → 异步不生效（走不到代理），报告变成同步阻塞。这是 Spring AOP 经典坑。
